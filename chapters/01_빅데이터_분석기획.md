# 1과목: 빅데이터 분석 기획

## 📋 과목 개요 & 출제 경향

**한 줄 요약**: 빅데이터를 "왜, 어떻게" 분석할지 기획하는 전체 과정을 다루는 과목.

**출제 범위**: 빅데이터의 이해 → 데이터 분석 기획 → 데이터 수집/저장 계획

**출제 경향**:
- 용어 정의와 특징을 묻는 문제가 가장 많음 (DIKW, 3V, 데이터베이스 특징 등)
- "다음 중 ~이 아닌 것은" 패턴이 압도적
- 순서를 묻는 문제 빈출 (CRISP-DM 절차, 빅데이터 분석 방법론 단계 등)
- 비교/매칭 문제 (집중구조 vs 기능구조 vs 분산구조 등)
- ADsP를 공부했다면 상당 부분 겹침, 법제도/인공지능/수집기술이 추가

> 💡 이 과목은 "외울 것이 많지만 이해하면 쉬운" 과목이다. 강의자가 제시하는 암기법(글자 따기)을 적극 활용하자.

**이 과목의 전체 흐름 — 큰 그림 먼저 잡기**:

```
┌─────────────────────────────────────────────────────────────────┐
│                    1과목 전체 로드맵                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1장: 빅데이터가 뭐야?        ← 기초 개념 (DIKW, 3V, DB)        │
│         ↓                                                       │
│  2장: 개인정보는 어떻게 보호해? ← 법률/윤리 (데이터3법, 비식별화)  │
│         ↓                                                       │
│  3장: 분석을 어떻게 기획해?    ← 분석 방향 잡기 (매트릭스, 접근법) │
│         ↓                                                       │
│  4장: 분석 방법론은 뭐가 있어? ← 체계적 절차 (CRISP-DM, KDD)     │
│         ↓                                                       │
│  5장: 우리 회사 분석 수준은?   ← 조직 진단 (준비도, 성숙도)       │
│         ↓                                                       │
│  6장: 데이터를 어떻게 모아?    ← 수집/저장 기술 (ETL, HDFS)       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

> 💡 **연결고리**: 1장에서 배운 DIKW 피라미드의 "데이터 → 지혜" 여정을 실현하려면, 2장의 법적 테두리 안에서, 3장처럼 기획하고, 4장의 방법론을 따르고, 5장으로 조직 역량을 점검하고, 6장의 기술로 데이터를 모아야 한다. 이 6개 장이 하나의 파이프라인이다.

## 1장: 빅데이터의 이해

### 1.1 데이터의 개념

**한 줄 요약**: 데이터는 "있는 그대로의 객관적 사실"이고, 가공하면 정보가 된다.

**왜 필요한가**: 빅데이터를 이해하려면 가장 기본인 "데이터가 뭔지"부터 정확히 알아야 한다. 시험에서도 데이터와 정보를 구분하는 문제가 나온다.

**핵심 설명**:

일상 비유: 마트에서 "오늘 사과 50개 팔림"이라는 숫자 자체가 **데이터**다. 이걸 가공해서 "사과가 이번 달 베스트셀러"라고 판단하면 그게 **정보**다.

- **데이터**: 가공되지 않은 객관적 사실 (예: 주문 수량 100개)
- **정보**: 데이터를 가공하여 패턴을 인식한 것 (예: 베스트셀러 상품)

그래서 실제로 어떻게 쓰이냐면... 병원에서 "오늘 외래 환자 253명"이라는 숫자는 데이터다. "월요일 오전에 환자가 집중되니 의사를 추가 배치하자"는 정보를 넘어 의사결정(지식)이다.

데이터는 두 가지 특성을 가진다:
- **존재적 특성**: 현실을 그대로 반영 (있는 그대로의 사실). 쉽게 말해 **"사실 자체"** — 해석 없이 그냥 존재하는 것. 예: 체온 36.5도 — 사실 그 자체
- **당위적 특성**: 맥락 속에서 의미를 부여할 수 있음. 쉽게 말해 **"의미 부여"** — 사실에 해석을 붙이는 것. 예: 체온 36.5도 → "정상 체온이다"라는 해석 가능

**⚠️ 시험 포인트**:
- "데이터는 객관적 사실이다" → O
- "데이터를 가공하면 정보가 된다" → O
- 데이터와 정보의 사례 매칭 문제 출제 가능

**시험 출제 예시**: "다음 중 '정보'에 해당하는 것은?" → (1) 매출액 5000만원 (2) 전월 대비 매출 20% 증가 (3) A제품 30개 판매 (4) 고객 수 200명 → 정답: (2) — 비교/가공이 들어가면 정보

### 1.2 DIKW 피라미드

**한 줄 요약**: 데이터 → 정보 → 지식 → 지혜로 올라가는 가치 상승 구조.

**왜 필요한가**: 빅데이터 분석의 궁극적 목적이 데이터에서 지혜까지 끌어올리는 것이므로, 이 피라미드가 전체 프레임워크가 된다. **시험에 정말 자주 출제된다.**

> 💡 **다른 장과의 연결**: 3장의 "분석 매트릭스"에서 What/How를 찾는 것도 결국 데이터(D)를 지혜(W)로 끌어올리기 위한 것이다. 4장의 CRISP-DM "업무 이해→전개"도 이 피라미드를 실현하는 구체적 절차다.

**핵심 설명**:

```
        ┌─────┐
        │ 지혜 │  ← 창의적 전략 수립 (아이디어 확장)
       ┌┴─────┴┐
       │  지식  │  ← 의사결정에 활용 (예측)
      ┌┴───────┴┐
      │   정보   │  ← 패턴 인식 (가공)
     ┌┴─────────┴┐
     │   데이터   │  ← 객관적 사실 (원시 상태)
     └───────────┘
```

**각 단계 사이에 무슨 일이 일어나는가?**

```
  데이터  ──[가공/비교]──→  정보  ──[경험/학습]──→  지식  ──[창의적 확장]──→  지혜
  "사실"                   "패턴"                  "판단"                    "통찰"
```

구체적인 사례로 이해해 보자:

| 단계 | 정의 | 사례 (핸드폰 가격) | 핵심 동사 |
|------|------|-------------------|----------|
| **데이터(D)** | 객관적 사실 | A대리점 100만원, B대리점 200만원 | 수집하다 |
| **정보(I)** | 패턴 인식 (가공) | A대리점이 B보다 싸다 | 비교하다 |
| **지식(K)** | 의사결정 활용 (예측) | A대리점에서 사면 이득이다 | 판단하다 |
| **지혜(W)** | 창의적 전략 (확장) | A대리점의 다른 기기들도 더 저렴하지 않을까? | 확장하다 |

> **구분 팁**: "비교"가 들어가면 정보, "~하면 좋겠다/이득이다"같은 판단이 들어가면 지식, "다른 분야로 확장"하면 지혜

**⚠️ 시험 포인트**:
- 각 단계의 정의를 정확히 구분해야 함
- 사례를 주고 "이것은 DIKW 중 무엇인가?" 형태로 출제
- 피라미드 순서: D → I → K → W (아래에서 위로)
- 시험이 쉬우면 순서, 어려우면 각 단계의 세부 특징 물어봄

**시험 출제 예시**: "고객 이탈 데이터를 분석해 30대 여성 고객의 이탈률이 높다는 패턴을 발견했다" → 이것은 **정보** 단계 (패턴 인식)

📝 보충: **DIKW 현실 예시 (커피숍 운영)**

| 단계 | 커피숍 사례 |
|------|-----------|
| **데이터** | 오늘 아메리카노 120잔, 라떼 80잔 판매 |
| **정보** | 아메리카노가 라떼보다 1.5배 많이 팔렸다 |
| **지식** | 오후 2시~4시에 아메리카노 주문이 집중되므로, 해당 시간대 원두를 미리 갈아놓으면 효율적이다 |
| **지혜** | 오후 시간대 직장인 대상 "아메리카노 + 디저트" 세트 메뉴를 만들면 매출이 오르지 않을까? |

📝 보충: **DIKW 현실 예시 (배달앱 운영)**

| 단계 | 배달앱 사례 |
|------|-----------|
| **데이터** | 금요일 저녁 치킨 주문 3,200건, 피자 주문 2,100건 |
| **정보** | 금요일 저녁에 치킨이 피자보다 1.5배 더 많이 주문된다 |
| **지식** | 금요일 저녁에는 치킨 배달 라이더를 추가 배치하면 배달 시간을 줄일 수 있다 |
| **지혜** | "금요일 저녁 치킨+맥주 묶음 할인"을 제공하면 주문 단가를 높이고, 다른 요일에도 비슷한 패턴이 있는지 탐색해볼 수 있지 않을까? |

### 1.3 암묵지와 형식지의 상호작용

**한 줄 요약**: 머릿속 경험(암묵지)을 문서화(형식지)하고 다시 내면화하는 지식 변환 과정.

**왜 필요한가**: 조직에서 지식을 어떻게 공유하고 발전시키는지를 설명하는 모델이다. 기출에 여러 번 출제됨.

**핵심 설명**:

비유: 내가 요리사라고 가정하자.

- **암묵지(Tacit Knowledge)**: 나만 알고 있는 요리 비법 (경험으로 체득한, 겉으로 드러나지 않은 지식). 비유하면 자전거 타는 법 — 말로 설명하기 어렵지만 몸이 기억하는 것.
- **형식지(Explicit Knowledge)**: 요리책이나 블로그에 작성한 레시피 (문서나 매뉴얼로 형상화된 지식). 비유하면 교과서 — 누구나 읽으면 알 수 있는 것.

이 둘 사이에는 4가지 상호작용이 일어난다:

```
            ┌──────────────────────────────────────────┐
            │            지식 변환 순환 구조              │
            │                                          │
            │    암묵지 ──[공통화]──→ 암묵지             │
            │      │                    │              │
            │   [내면화]             [표출화]           │
            │      │                    │              │
            │    형식지 ←──[연결화]──← 형식지            │
            │                                          │
            └──────────────────────────────────────────┘
```

> 이 모델의 정식 명칭은 **SECI 모델**(노나카 이쿠지로)이며, 각 단계의 영어 첫 글자를 딴 것이다.

| 변환 | 영어 | 방향 | 설명 | 요리사 비유 | 회사 비유 |
|------|------|------|------|------------|----------|
| **공통화** | **S**ocialization | 암묵지 → 암묵지 | 경험을 타인에게 직접 전수 | 조수에게 요리 지식을 알려줌 | 선배가 후배에게 OJT |
| **표출화** | **E**xternalization | 암묵지 → 형식지 | 경험을 문서로 형상화 | 요리 블로그/책에 레시피 작성 | 업무 매뉴얼 작성 |
| **연결화** | **C**ombination | 형식지 → 형식지 | 기존 문서에 새 지식 추가/보완 | 레시피 연구 후 블로그 내용 보완 | 기존 보고서를 종합하여 새 보고서 작성 |
| **내면화** | **I**nternalization | 형식지 → 암묵지 | 문서를 읽고 자기 것으로 터득 | 다른 사람이 블로그 보고 요리 습득 | 매뉴얼 보고 실무에서 직접 체득 |

> 암기법: **"공표연내"** (공통화 → 표출화 → 연결화 → 내면화)

**⚠️ 시험 포인트**:
- "공표연내" 순서 암기 필수
- 각 변환의 방향(암묵지↔형식지)을 정확히 구분
- (💡 2025ver 보충) 최근에는 시험에 잘 안 나오고 있지만 기출에 여러 번 출제된 적이 있으므로 익혀둘 것

**시험 출제 예시**: "숙련 직원이 신입 직원에게 업무 노하우를 직접 시범으로 전수하는 것" → **공통화** (암묵지→암묵지). "시범 전수 후 이를 매뉴얼로 문서화" → **표출화** (암묵지→형식지)

### 1.4 데이터베이스

**한 줄 요약**: 데이터를 체계적으로 저장하는 저장소로, 4가지 핵심 특징을 가진다.

**왜 필요한가**: 빅데이터의 기반이 되는 저장소 개념을 모르면 뒤의 모든 내용이 공중에 뜬다. **시험에 정말 자주 출제된다.**

> 💡 **다른 장과의 연결**: 여기서 배우는 DB 개념이 6장의 HDFS(분산 파일 시스템), NoSQL, 데이터 웨어하우스의 기반이 된다. "데이터를 어디에 저장하느냐"가 분석의 출발점이기 때문.

**핵심 설명**:

비유: 데이터베이스를 **창고**라고 생각하자. 회사의 인사 데이터베이스에는 직원 정보가, 학교의 학생 데이터베이스에는 학생 정보가 들어 있다.

그래서 실제로 어떻게 쓰이냐면... 여러분이 쇼핑몰에서 주문하면, 주문 내역이 DB에 저장된다. 배송 조회하면 DB에서 꺼내 보여주는 것이다. 은행 앱에서 잔액 조회하면 DB에서 읽어오고, 이체하면 DB를 업데이트한다.

#### 데이터베이스의 4가지 특징

> 암기법: **"공통저변"**

| 특징 | 설명 | 쉬운 표현 | "이게 아니면?" |
|------|------|----------|--------------|
| **공용 데이터** | 여러 부서가 다른 목적으로 공동 이용 | 인사부서도, 재무부서도 같은 DB 사용 | 한 부서만 독점하면 공용 아님 |
| **통합 데이터** | 동일 데이터가 중복 저장되면 안 됨 | 같은 정보 2번 저장 = 공간 낭비 | 중복 저장되면 통합 아님 |
| **저장 데이터** | 저장 매체에 물리적으로 저장 | 컴퓨터 디스크에 실제로 존재 | 머릿속에만 있으면 DB 아님 |
| **변화 데이터** | 계속 변화하지만 정확성(무결성) 유지 | 데이터가 바뀌어도 결함이 없어야 함 | 변화 없이 고정이면 DB의 의미 없음 |

> **비교표에서 이 차이가 왜 중요한가?** 시험에서 "통합 데이터의 특징으로 옳은 것은?" 형태로 나올 때, "중복 최소화"를 고르면 정답이고, "여러 부서가 공동 사용"을 고르면 "공용 데이터"와 혼동한 것이다. 4가지가 각각 다른 측면을 설명하므로 섞이지 않게 구분해야 한다.

#### 데이터베이스 관련 핵심 용어

데이터베이스를 창고에 비유하면:

| 용어 | 비유 | 정의 | 현실 예시 |
|------|------|------|----------|
| **스키마(Schema)** | 창고 건축 도면 | DB의 전반적인 명세(구조 설계) | "고객 테이블은 이름, 나이, 주소 컬럼이 있다"는 설계도 |
| **메타데이터** | 물건에 붙은 라벨 | 데이터를 설명하는 데이터 (이름, 규격, 제조일자 등) | 사진 파일의 촬영 날짜, 위치, 카메라 정보 |
| **데이터 사전** | 관리자 책상의 종합 안내 책자 | 어떤 물건이 있고, 어떤 라벨이 붙었는지 정리한 목록 | "어떤 테이블이 있고, 각 컬럼이 뭔지" 정리한 문서 |
| **인스턴스** | 창고에 저장된 물건 그 자체 | DB에 실제 저장된 데이터 값 | 고객 테이블에 실제로 들어있는 "홍길동, 25, 서울" |
| **인덱스** | 물건 위치를 미리 적어둔 구역표 | 정렬/탐색을 위한 보조 도구 | 책 뒤의 색인(Index) — "ㄱ: 가격 p.5, 거래 p.12" |

> **메타데이터 쉽게 기억하기**: 도서관에서 책 내용은 "데이터"이고, 도서관 카드에 적힌 "저자, 출판년도, 분류번호"는 "메타데이터"다. 데이터를 찾고 관리하기 위한 데이터.

#### 데이터베이스 설계 순서

> 암기법: **"개논물"** (개념적 → 논리적 → 물리적)

1. **개념적 설계**: 대략적인 구조 설계 — "고객 정보와 주문 정보가 필요하다" 수준
2. **논리적 설계**: 컴퓨터가 이해할 수 있는 형태로 변환 — "고객(고객ID, 이름, 연락처)" 수준
3. **물리적 설계**: 실제 저장 매체에 저장 — "이 테이블은 SSD에 저장, 인덱스는 이렇게" 수준

```
개념적 설계          논리적 설계              물리적 설계
(뭐가 필요해?)  →  (어떤 구조로?)     →   (어디에 어떻게 저장?)
  대략적 구조        테이블/컬럼 정의        저장매체, 인덱스 설정
```

#### DBMS (Database Management System)

DB에 직접 접근할 수 없고, **DBMS라는 소프트웨어**를 통해 접근한다. DB를 관리하고 접근 환경을 제공하는 소프트웨어.

그래서 실제로 어떻게 쓰이냐면... 여러분이 은행 앱에서 "잔액 조회" 버튼을 누르면, 앱이 DBMS에 "이 사람 잔액 알려줘"라고 요청하고, DBMS가 DB에서 찾아서 알려주는 것이다. 직접 DB 파일을 열어보는 게 아니다.

두 가지 형태:
- **관계형 DBMS (RDBMS)**: 전통적인 DB. 테이블(표) 형태로 정리. 정형 데이터 저장. 비유하면 **엑셀 시트**처럼 행과 열이 딱 정해진 구조.
- **NoSQL DBMS**: 빅데이터 시대에 등장. SNS 글, 유튜브 영상 등 비정형 데이터 저장/관리. 비유하면 **메모장**처럼 자유롭게 아무거나 넣을 수 있는 구조.

#### SQL (Structured Query Language)

DB에 접근할 때 사용하는 **국제 표준 언어**. 컴퓨터에게 "이 데이터 찾아줘"라고 말하는 언어.

| 종류 | 풀네임 | 역할 | 비유 | 주요 명령어 |
|------|--------|------|------|-----------|
| **DDL** | Data Definition Language | DB 구조를 만들거나 바꿈 | "설계도 그리기" | CREATE, ALTER, DROP |
| **DML** | Data Manipulation Language | 데이터를 넣고 빼고 수정 | "실제 물건 다루기" | SELECT, INSERT, UPDATE, DELETE |
| **DCL** | Data Control Language | 접근 권한 관리 | "출입증 관리" | GRANT, REVOKE |

> **DDL/DML/DCL 구분 팁**: Definition=정의(구조), Manipulation=조작(데이터), Control=통제(권한). D-D-M-C의 두 번째 글자로 기억!

**⚠️ 시험 포인트**:
- "공통저변" 4가지 특징 → 단골 출제
- 메타데이터 = "데이터를 설명하는 데이터" → 정의 자주 물어봄
- 스키마의 3가지 종류 참고로 알아둘 것:
  - **외부 스키마**: 사용자 관점에서 본 DB 구조 (사용자마다 다르게 보임). 비유: "내가 보는 화면"
  - **개념 스키마**: DB 전체의 논리적 구조 (하나만 존재). 비유: "전체 설계도"
  - **내부 스키마**: 실제 물리적 저장 방식 (디스크에 어떻게 저장?). 비유: "창고 배치도"
- RDBMS vs NoSQL 구분
- 10회 기출: "데이터 분석에 필요한 기반 환경" → 인프라스트럭처

**시험 출제 예시**: "데이터베이스의 특징 중 '동일한 데이터가 중복되어 저장되지 않는 것'에 해당하는 것은?" → **통합 데이터** (공용/저장/변화와 혼동 주의)

### 1.5 데이터베이스의 기업 활용

**한 줄 요약**: 기업에서 DB를 활용하는 다양한 시스템들을 약어의 의미로 구분한다.

**왜 필요한가**: 시험에서 각 시스템의 약어와 특징을 매칭하는 문제가 나온다.

**핵심 설명**:

> 암기법: **약어의 풀네임(Full Name)을 외우면 뉘앙스로 구분 가능**

| 약어 | 풀네임 키워드 | 핵심 의미 | 시험 포인트 | 현실 예시 |
|------|-------------|----------|------------|----------|
| **OLTP** | **T**ransaction | 거래 단위 처리 | "거래" 느낌 나오면 OLTP | ATM에서 출금할 때 잔액 차감 |
| **OLAP** | **A**nalytics | 다차원 데이터 대화식 분석 | "분석" 느낌 나오면 OLAP | "지역별/월별 매출 비교" 피벗 테이블 |
| **CRM** | **C**ustomer **R**elation | 고객 관계 관리 | "고객" 나오면 CRM | 고객 등급 관리, 멤버십 포인트 |
| **SCM** | **S**upply **C**hain | 공급망 연결 관리 | "공급" 나오면 SCM | 원자재 주문→제조→유통→판매 추적 |
| **ERP** | **E**nterprise **R**esource | 기업 자원 관리 | "기업 자원" 나오면 ERP | SAP 같은 통합 시스템 |
| **RTE** | **R**eal **T**ime | 실시간 신속 의사결정 | "실시간" 나오면 RTE | 실시간 주가 대응 시스템 |
| **BI** | **B**usiness **I**ntelligence | 기업 보고서/통찰력 | "보고, 통찰" 나오면 BI | 대시보드로 경영진에게 보고 |
| **블록체인** | - | 네트워크 참여자가 정보를 분산 저장 | 비트코인 연상 | 암호화폐, NFT |
| **KMS** | **K**nowledge Management | 지식 관리 시스템 | "지식" 나오면 KMS | 사내 위키, 지식 포털 |

📝 보충: **OLAP 주요 연산 5종** (다차원 데이터를 다양한 각도로 분석하는 연산들)

| 연산 | 설명 | 예시 |
|------|------|------|
| **Roll-up** | 세부 → 상위로 요약 (집계) | 일별 매출 → 월별 매출로 합산 |
| **Drill-down** | 상위 → 세부로 내려감 (Roll-up의 반대) | 월별 매출 → 일별 매출로 상세 조회 |
| **Slice** | 한 차원의 특정 값으로 잘라냄 (1개 조건) | "서울"만 필터링해서 보기 |
| **Dice** | 여러 차원의 조건으로 잘라냄 (다중 조건) | "서울" + "2024년" + "전자제품"으로 필터링 |
| **Pivot** | 축을 회전시켜 다른 관점으로 봄 | 행에 있던 "지역"을 열로 옮겨서 비교 (엑셀 피벗 테이블과 동일) |

**OLTP vs OLAP — 가장 많이 혼동하는 개념**:

```
  OLTP (거래 처리)              OLAP (분석 처리)
  ──────────────                ──────────────
  "지금 이 주문 처리해"          "지난 3개월 매출 추이 보여줘"
  한 건씩 빠르게                 대량 데이터 한꺼번에
  현재 데이터                    과거~현재 데이터
  은행 ATM, POS                  경영진 대시보드, 보고서
```

**⚠️ 시험 포인트**:
- 약어와 설명을 매칭시키는 문제 출제
- OLTP(거래)와 OLAP(분석) 혼동 주의
- 10회 기출: "OLTP는 대용량 비정형 데이터 분석에 적합한 기술이다" → **틀림** (OLTP는 관계 DBMS 거래 처리 기술)

### 1.6 빅데이터의 등장 배경

**한 줄 요약**: 클라우드 컴퓨팅과 분산 처리 기술의 발전으로 빅데이터 시대가 열렸다.

**왜 필요한가**: 빅데이터가 "왜" 등장했는지를 이해하면 빅데이터의 특성도 자연스럽게 이해된다.

**핵심 설명**:

두 가지 핵심 배경:

1. **클라우드 컴퓨팅 등장**: 
   - 과거: 직접 저장 매체를 구매해야 했음 (USB, 외장하드 등)
   - 현재: 구글 드라이브, 네이버 드라이브 등으로 네트워크만 있으면 저장 가능
   - 수요가 있을 때마다(**온디맨드**) 구독으로 이용 — 비유하면 물을 직접 우물 파지 않고 수도꼭지만 틀면 나오는 것
   - 저장 매체 가격 하락 → 경제성 확보

2. **분산 처리 기술 발달**:
   - **하둡(Hadoop)**: 여러 컴퓨터를 하나로 묶어 대용량 데이터를 처리하는 오픈소스 솔루션
   - 비유하면 이사할 때 혼자 짐 나르면 하루 걸리지만, 친구 10명이 나눠서 나르면 1시간이면 끝나는 것
   - 분산 컴퓨팅으로 처리 속도 향상

(💡 2025ver 보충) 인터넷 확산, 스마트폰 보급도 빅데이터 출현 배경에 포함

#### 클라우드 서비스 모델 (IaaS / PaaS / SaaS)

**한 줄 요약**: 클라우드 서비스는 제공 범위에 따라 IaaS, PaaS, SaaS 3계층으로 나뉜다.

**왜 필요한가**: 빅데이터 인프라를 구축할 때 어떤 클라우드 서비스를 선택할지 결정해야 하고, 시험에서 3가지 모델의 차이를 묻는 문제가 출제된다.

**핵심 설명**:

비유하면 피자를 먹는 3가지 방법이다:
- **IaaS**: 밀가루, 오븐, 치즈를 빌려서 직접 만듦 (인프라만 빌림)
- **PaaS**: 반죽과 소스가 준비된 키트를 받아서 토핑만 올림 (개발 환경까지 빌림)
- **SaaS**: 완성된 피자를 배달시켜 먹음 (완제품 서비스를 이용)

| 모델 | 풀네임 | 제공 범위 | 사용자 역할 | 예시 |
|------|--------|----------|-----------|------|
| **IaaS** | Infrastructure as a Service | 서버, 스토리지, 네트워크 | OS/미들웨어/앱 직접 설치 | AWS EC2, Azure VM |
| **PaaS** | Platform as a Service | IaaS + OS + 개발 환경 | 애플리케이션만 개발 | Google App Engine, Heroku |
| **SaaS** | Software as a Service | 모든 것 포함 (완제품) | 그냥 사용 | Gmail, Google Docs, Salesforce |

```
제공 범위 비교:

           IaaS         PaaS         SaaS
         ┌────────┐  ┌────────┐  ┌────────┐
사용자    │ 앱     │  │        │  │        │
관리 영역 │ 미들웨어│  │ 앱     │  │        │
         │ OS     │  │        │  │ (없음) │
         ├────────┤  ├────────┤  ├────────┤
클라우드  │ 서버   │  │ 미들웨어│  │ 전부   │
제공 영역 │ 스토리지│  │ OS     │  │ 제공   │
         │ 네트워크│  │ 서버   │  │        │
         └────────┘  └────────┘  └────────┘
```

> 암기법: **"아(I)빠(P)싸(S)"** — I(인프라)만 → P(플랫폼)까지 → S(소프트웨어) 전부. 갈수록 사용자가 편하고 자유도는 줄어든다.

**⚠️ 시험 포인트**:
- "~as a Service" 이름과 제공 범위 매칭 문제 출제
- IaaS는 자유도 최대/관리 부담 최대, SaaS는 자유도 최소/관리 부담 최소
- "온디맨드(On-Demand)" = 필요할 때 필요한 만큼 사용하는 클라우드의 핵심 특성

### 1.7 빅데이터의 3V와 데이터 단위

**한 줄 요약**: 빅데이터는 규모(Volume), 다양성(Variety), 속도(Velocity)의 3V 특징을 가진다.

**왜 필요한가**: 3V는 빅데이터를 정의하는 가장 핵심적인 특징으로, 거의 매 시험에 출제된다.

**핵심 설명**:

#### 빅데이터 3V (가트너 정의)

**가트너(Gartner)**: 미국의 IT 자문 기관. 공신력이 매우 높다. 비유하면 IT 업계의 "미쉐린 가이드".

| V | 영어 | 의미 | 현실 예시 |
|---|------|------|----------|
| **Volume** | 규모 | 데이터의 양이 방대함 | 유튜브에 매분 500시간 영상 업로드 |
| **Variety** | 다양성 | 정형/반정형/비정형 등 다양한 형태 | 텍스트, 사진, 영상, 센서 데이터 등 |
| **Velocity** | 속도 | 데이터 생성/처리 속도가 빠름 | 주식 거래 데이터 밀리초 단위 생성 |

```
         빅데이터 3V
        ┌─────────┐
       /  Volume  / \
      /   (규모)  /   \
     ┌──────────┐     \
     │ Variety  │ Velocity
     │ (다양성) │  (속도)
     └──────────┘
  3V 모두 충족해야 "빅데이터"!
```

- 5V, 7V로 확장 시 추가되는 V들 (각각 한 줄 정의):
  - **Value(가치)**: 데이터에서 실제로 뽑아낼 수 있는 비즈니스 가치
  - **Veracity(정확성/신뢰성)**: 데이터가 얼마나 정확하고 믿을 수 있는가
  - **Visualization(시각화)**: 분석 결과를 그래프/차트로 보여주는 것
  - **Variability(가변성)**: 데이터의 의미나 맥락이 시간에 따라 달라지는 것
  - **Validity(유효성)**: 데이터가 분석 목적에 맞게 수집되었는가
- 시험에 "3V가 아닌 것은?" → Value, Veracity 등이 오답 보기로 등장

> **주의**: Value(가치)는 3V에 포함되지 않는다! 하지만 분석 프로젝트 우선순위(3.4절)에서는 시급성 기준으로 Value가 등장한다. 혼동 금지.

#### 데이터 단위 (용량 순서)

```
바이트(B) → 킬로(KB) → 메가(MB) → 기가(GB) → 테라(TB)
→ 페타(PB) → 엑사(EB) → 제타(ZB) → 요타(YB)
```

> 암기법: 테라 이후 **"페지요"** (페타 → 엑사(지) → 제타 → 요타)
> (강의자: "꼴보기 싫은 선배를 해고 싶죠? 폐지요!")

| 단위 | 2의 거듭제곱 | 크기 감각 |
|------|------------|----------|
| 페타바이트 | 2^50 | 미 의회 도서관 전체 장서의 약 50배 |
| 엑사바이트 | 2^60 | 전 세계 1년 인터넷 트래픽 수준 |
| 제타바이트 | 2^70 | 현재 전 세계 디지털 데이터 총량 |
| 요타바이트 | 2^80 | 아직 현실에서 도달하지 못한 크기 |

📝 **계산 예시 — 데이터 단위 환산**:
- 1PB = 2^50 바이트 = **1,024TB**
- 문제: "5TB는 몇 GB인가?" → 5 × 1,024 = **5,120GB**
- 문제: "2EB는 몇 PB인가?" → 2 × 1,024 = **2,048PB**
- 핵심: 인접 단위 간 **1,024배** (= 2^10). 시험에서 "KB→MB→GB→TB→PB→EB→ZB→YB" 순서와 배수 관계 출제

**⚠️ 시험 포인트**:
- "빅데이터 3V가 아닌 것은?" → 단골 출제
- 시험이 어려우면 각 V의 세부 설명 물어봄
- 데이터 단위 순서 및 2의 거듭제곱 관계 출제
- 가트너(Gartner)가 3V를 정의했다는 사실도 중요

### 1.8 빅데이터 활용 3대 요소

**한 줄 요약**: 빅데이터를 활용하려면 인력, 자원(데이터), 기술 세 가지가 필요하다.

**왜 이 세 가지인가?** 아무리 좋은 데이터(자원)가 있어도 분석할 사람(인력)이 없으면 무용지물이고, 사람이 있어도 분석 도구(기술)가 없으면 실행 불가. 삼각대의 다리처럼 하나라도 빠지면 서 있을 수 없다.

```
        ┌──────┐
        │ 인력  │  ← 데이터 사이언티스트, 분석가
        └──┬───┘
           │
    ┌──────┴──────┐
    │              │
┌───┴──┐    ┌──────┴───┐
│ 자원  │    │   기술    │
│(데이터)│    │(하둡,R등)│
└──────┘    └──────────┘

세 요소가 균형을 이뤄야 빅데이터 활용 가능!
```

- **인력**: 데이터 사이언티스트, 분석가 등 전문 인력
- **자원(데이터)**: 분석할 원재료. 양과 질 모두 중요
- **기술**: 하둡, 스파크, R/Python 등 분석 인프라와 도구

> 암기법: **"인자기"** (인력, 자원, 기술) — 이탈리아 축구 선수 인자기(Inzaghi) 연상

그래서 실제로 어떻게 쓰이냐면... 넷플릭스가 추천 시스템을 만들려면: (1) 데이터 사이언티스트(**인력**), (2) 시청 기록 데이터(**자원**), (3) 추천 알고리즘 및 서버(**기술**) 세 가지가 모두 필요하다.

**⚠️ 시험 포인트**:
- "빅데이터 활용 3대 요소가 아닌 것은?" → 보기에 "프로세스" 같은 그럴듯한 오답 포함

### 1.9 빅데이터 가치 산정이 어려운 이유

**한 줄 요약**: 빅데이터는 누가, 언제, 어떻게 활용할지 예측 불가하고, 새 분석 기법이 새 가치를 만들어낼 수 있다.

- 데이터가 너무 광범위 → 언제 어디서 누가 활용할지 알 수 없음
- 현재 가치 없는 데이터도 새로운 분석 기법 등장 시 새 가치 창출 가능

그래서 실제로 어떻게 쓰이냐면... GPS 위치 데이터는 원래 군사 목적이었지만, 스마트폰 시대가 오면서 배달앱, 내비게이션, 부동산 분석 등 전혀 다른 가치를 만들어냈다. 데이터 수집 당시에는 이런 활용을 예측할 수 없었다.

### 1.10 빅데이터가 만들어내는 변화

**한 줄 요약**: 표본→전수, 사전→사후, 질→양, 인과→상관으로 패러다임이 전환되었다.

**왜 필요한가**: **시험 단골 출제**. 빅데이터 시대 이전과 이후의 변화를 정확히 구분해야 한다.

> 암기법: **"전후양상"**

| 구분 | 이전 (과거) | 이후 (빅데이터 시대) | 암기 키워드 | 왜 바뀌었나? |
|------|-----------|-------------------|-----------|-------------|
| 조사 방식 | 표본 조사 | **전**수 조사 | **전** | 저장/처리 비용이 떨어져서 전체 데이터 분석 가능 |
| 처리 시점 | 사전 처리 | 사**후** 처리 | **후** | 데이터가 워낙 많아서 먼저 모으고 나중에 처리 |
| 중요도 | 데이터의 질 | 데이터의 **양** | **양** | 양이 충분하면 약간의 오류는 상쇄됨 |
| 분석 관점 | 인과 관계 | **상**관 관계 | **상** | "왜?"보다 "무엇이 함께 일어나는가?"가 중요 |

**각 변화를 현실 예시로 이해하기**:

```
  [표본→전수]
  과거: 1000명 중 100명 설문조사
  현재: SNS 데이터로 1000만 명 전수 분석

  [사전→사후]
  과거: "이 데이터가 필요할 것 같으니 미리 형식 맞춰서 수집"
  현재: "일단 다 모아놓고, 나중에 필요할 때 꺼내서 분석"

  [질→양]
  과거: 정확한 100개 데이터로 분석
  현재: 약간 부정확하더라도 100만 개 데이터로 분석 → 더 정확

  [인과→상관]
  과거: "맥주를 사는 이유가 뭐지?" (원인 분석)
  현재: "맥주와 기저귀가 함께 팔린다" (상관관계 발견)
```

**⚠️ 시험 포인트**:
- "전후양상" 네 가지 변화 → **정말 자주 출제된다** (강의자 강조)
- "표본조사 → 전수조사" 같은 변환 방향을 묻는 문제
- 시험이 쉬우면 순서, 어려우면 각 변화의 세부 설명
- **함정**: "양 → 질"로 순서를 뒤집어 놓는 보기 조심! 빅데이터 시대는 "질 → 양"이다.

### 1.11 빅데이터 가치 패러다임 변화

**한 줄 요약**: 디지털화 → 연결 → 에이전시 순으로 패러다임이 변화했다.

> 암기법: **"디커에(디지털, 커넥션, 에이전시)"** 또는 **"디지털 카메라"**로 연상

| 단계 | 설명 | 현실 예시 |
|------|------|----------|
| 디지털화 | 아날로그에서 디지털로 전환 | 종이 문서 → 전자 문서, LP → MP3 |
| 연결(커넥션) | 디지털 정보가 서로 연결 | SNS로 사람과 정보가 연결, IoT 센서 간 통신 |
| 에이전시 | 연결된 정보가 스스로 행동하는 주체가 됨 | AI 비서가 알아서 일정 관리, 자율주행차 |

> **왜 이 순서인가?** 아날로그를 디지털로 바꿔야(디지털화) 연결할 수 있고, 연결되어야(커넥션) 스스로 판단하고 행동하는 단계(에이전시)로 넘어갈 수 있다. 이전 단계가 다음 단계의 필수 전제 조건이다.

> **"에이전시(Agency)"란?** "자율적으로 행동하는 능력"을 뜻하는 용어다. 데이터가 단순히 연결되어 있는 것을 넘어, **스스로 판단하고 실행**하는 수준. 비유하면 스마트홈에서 온도 센서가 "춥다"는 데이터를 감지(디지털화) → 다른 기기와 연결(커넥션) → 보일러를 자동 가동(에이전시).

**⚠️ 시험 포인트**: 시험이 쉬우면 순서, 어려우면 각 단계의 세부 특징 물어봄

(💡 2025ver 보충) **데이터 산업 발전 과정**: 프로그래밍 언어 → 데이터베이스 등장 → 분석 기술 발전 → 모듈 연결 → **마이 데이터** 등장 (자신의 신용 정보를 제3자에게 제공하여 서비스를 제공받는 제도. 은행/금융 앱에서 직접 가입 가능한 것이 이 개념). 쉬운 예시: 은행 앱 하나에서 내가 가진 모든 은행 계좌, 카드 사용 내역, 보험 정보를 한 번에 모아 볼 수 있는 것 — 이것이 마이데이터 서비스다.

### 1.12 데이터 사이언스와 데이터 사이언티스트

**한 줄 요약**: 데이터 관련 모든 분야를 종합한 학문이 데이터 사이언스이고, 이를 연구하는 사람이 데이터 사이언티스트다.

**핵심 설명**:

**데이터 사이언스**는 세 가지 영역의 교집합:

```
       분석학
      (수학,통계)
        /   \
       /     \
      / 데이터 \
     / 사이언스 \
    /─────────────\
  IT              비즈니스
(프로그래밍)      (도메인지식)
```

1. **분석학** (수학, 확률, 머신러닝) — "어떻게 분석할까?"
2. **IT** (프로그래밍, 기술) — "무엇으로 분석할까?"
3. **비즈니스** (도메인 지식) — "왜 분석할까?"

그래서 실제로 어떻게 쓰이냐면... 쿠팡의 데이터 사이언티스트는 통계학으로 배송 시간을 예측하고(분석학), Python으로 모델을 구현하고(IT), 물류 업무를 이해해서 실무에 적용한다(비즈니스). 세 가지가 하나라도 빠지면 제대로 된 분석이 안 된다.

**데이터 사이언티스트**의 필요 역량:

| 구분 | 느낌 | 예시 | 구분 팁 |
|------|------|------|--------|
| **하드 스킬** | 이과적 | 통계, 프로그래밍, 머신러닝 | "기술적으로 할 줄 아느냐" |
| **소프트 스킬** | 문과적 | 커뮤니케이션, 비즈니스 이해, 협업 | "사람과 잘 일하느냐" |

📝 보충: **가트너가 정의한 데이터 사이언티스트 4가지 역량**

| 역량 | 설명 | 예시 |
|------|------|------|
| **통계/수학** | 데이터를 수리적으로 분석하는 능력 | 회귀분석, 가설검정 |
| **IT/프로그래밍** | 분석 도구를 다루는 기술력 | Python, R, SQL |
| **비즈니스 분석** | 업무 맥락을 이해하고 분석 결과를 해석하는 능력 | "이탈률 감소가 매출에 미치는 영향" 해석 |
| **커뮤니케이션** | 분석 결과를 비전문가에게 설명하는 능력 | 경영진 대상 시각화 보고서 |

**⚠️ 시험 포인트**:
- "하드 스킬이 아닌 것은?" / "소프트 스킬이 아닌 것은?" 형태 출제
- 이과적 느낌 = 하드, 문과적 느낌 = 소프트로 구분
- 10회 기출: "데이터 사이언티스트의 일반적 역할이 아닌 것?" → 인사/인력 관리는 인사부서 업무

### 1.13 빅데이터 조직 구조

**한 줄 요약**: 기업 내 빅데이터 조직을 어떻게 운영할지 집중/기능/분산 세 가지 구조가 있다.

> 암기법: **"집기분"** (집중, 기능, 분산)

| 구조 | 특징 | 장점 | 단점 | 비유 |
|------|------|------|------|------|
| **집중 구조** | 독립적 전담 빅데이터 조직 구성 | 전문성 높음, 표준화/통합 관리 | 현업 부서와 소통 부족 시 중복 업무 | 회사에 "데이터 분석 전담팀" 신설 |
| **기능 구조** | 각 부서에서 직접 데이터 사이언티스트 양성 | 현업 이해도 높음 | 전사적 일관성 부족 | 마케팅팀, 물류팀 각각 자기 분석가 보유 |
| **분산 구조** | 분석 조직 인력을 현업 부서에 배치(파견) | 현업에 빠르게 적용/확산 | - | 본사 분석팀에서 각 부서에 분석가 파견 |

```
  【집중 구조】          【기능 구조】          【분산 구조】
  
  ┌──────────┐         마케팅팀[분석가]        본사 분석팀
  │ 분석 전담 │         물류팀[분석가]         ↙  ↓  ↘
  │   조직    │         인사팀[분석가]       A팀  B팀  C팀
  └──────────┘         (각자 양성)          (파견 배치)
  (독립 운영)
```

> **세 구조의 차이가 왜 중요한가?** 시험에서 "이 설명은 어떤 구조인가?"를 묻기 때문이다. 핵심 구분 키워드: **별도/독립 → 집중**, **각 부서에서 자체 양성 → 기능**, **파견/배치 → 분산**

**⚠️ 시험 포인트**:
- 시험이 쉬우면 보기에 "복합 구조" 같은 없는 용어를 넣어 놓음
- 시험이 어려우면 각 구조의 특징을 구분하는 문제
- 10회 기출: "집중형 조직 구조에 대한 설명으로 옳은 것은?" → "현업 부서에 빠르게 적용/확산 유리" = **분산** 구조 (집중형이 아님!)
- **"별도 부서 구성하여 전문 관리"** → 집중형
- **"현업 부서에 빠르게 적용 확산"** → 분산형

### 1.14 빅데이터 플랫폼

**한 줄 요약**: 빅데이터 분석의 전 과정(파이프라인)을 통합적으로 제공하는 환경.

**핵심 설명**:

각 부서가 따로따로 빅데이터 분석을 하면 비효율적이다. 통합 플랫폼을 만들면 새 부서도 연결만 하면 된다.

비유하면 주방(인프라)에 가스레인지, 냉장고, 조리도구(플랫폼)가 갖춰져 있어야 요리(분석)를 할 수 있고, 완성된 요리를 손님에게 제공(소프트웨어)하는 것.

#### 3계층 구조

```
┌──────────────────────────────┐
│     소프트웨어 계층            │  ← 사용자가 사용하는 애플리케이션
│  (대시보드, 보고서, 앱)        │     비유: 완성된 요리를 손님에게 제공
├──────────────────────────────┤
│      플랫폼 계층              │  ← 분석 도구, 시각화 도구
│  (분석 엔진, 라이브러리)       │     비유: 가스레인지, 조리도구
├──────────────────────────────┤
│   인프라스트럭처 계층          │  ← 하드웨어, 네트워크, 저장소
│  (서버, 스토리지, 네트워크)     │     비유: 주방 공간, 전기, 수도
└──────────────────────────────┘
```

#### 협의 vs 광의 분석 플랫폼

| 구분 | 대상 | 구성 요소 |
|------|------|----------|
| **협의(좁은 의미)** | 전문 분석가 관점 | 데이터 처리 프레임워크, 분석 엔진, 분석 라이브러리 |
| **광의(넓은 의미)** | 일반 사용자 포함 | 협의 + 제공 엔진, 어플리케이션, API, 하드웨어, OS |

> **협의 vs 광의 차이가 왜 중요한가?** 시험에서 "분석 플랫폼에 포함되지 않는 것은?"을 물을 때, 협의인지 광의인지에 따라 답이 달라질 수 있다.

**⚠️ 시험 포인트**:
- 3계층의 구분과 각 계층에 포함되는 요소
- 10회 기출: "서비스 계층에서 수행하는 기능?" → 데이터 및 정보를 제공 (사용자 단)
- 10회 기출: "데이터 분석에 필요한 기반 환경" = **인프라스트럭처**

### 1.15 빅데이터와 인공지능

**한 줄 요약**: 인공지능 > 머신러닝 > 딥러닝의 포함 관계를 갖고, 학습 방법에 따라 네 가지로 분류된다.

**핵심 설명**:

#### AI/ML/DL 관계

```
┌────────────────────────────────┐
│        인공지능 (AI)             │  ← 인간처럼 사고하는 기술
│  ┌──────────────────────────┐  │
│  │     머신러닝 (ML)          │  │  ← 데이터에서 패턴을 학습
│  │  ┌────────────────────┐  │  │
│  │  │   딥러닝 (DL)        │  │  │  ← 인간의 뇌(인공신경망) 모방
│  │  └────────────────────┘  │  │
│  └──────────────────────────┘  │
└────────────────────────────────┘
```

비유하면:
- **AI**: "지능적인 기계"라는 큰 꿈 (1950년대부터)
- **ML**: 그 꿈을 실현하는 방법 중 하나 — "데이터를 많이 보여주면 스스로 배운다"
- **DL**: ML의 한 갈래 — "뇌 구조를 흉내 내서 더 복잡한 것도 배운다"

그래서 실제로 어떻게 쓰이냐면... 스팸 메일 필터(ML)는 수천 개의 스팸/정상 메일을 보고 패턴을 학습한다. 얼굴 인식(DL)은 수백만 장의 사진으로 학습한 인공신경망이 사람 얼굴을 구분한다.

#### 머신러닝의 4가지 종류

| 종류 | 정답 제공 | 설명 | 비유 | 현실 예시 |
|------|----------|------|------|----------|
| **지도 학습** | O | 정답(레이블)을 알려주고 학습 | "이건 강아지야, 이건 고양이야" | 스팸 메일 분류, 집값 예측 |
| **비지도 학습** | X | 정답 없이 스스로 특징 발견/구분 | "알아서 구분해 봐" | 고객 세분화(군집 분석) |
| **준지도 학습** | △ | 지도+비지도 혼합 | 정답 있는 것 + 없는 것 섞어서 학습 | 일부만 라벨 붙인 이미지로 학습 |
| **강화 학습** | 보상 | 보상을 얻기 위해 스스로 학습 | 알파고: 바둑을 이기기 위해 반복 학습 | 게임 AI, 로봇 제어 |

> **4가지 구분 팁**: 정답을 줬나? → 지도. 안 줬나? → 비지도. 좀 줬나? → 준지도. 보상을 줬나? → 강화.

#### 인공지능 수준 분류

| 수준 | 설명 | 현재 상태 |
|------|------|----------|
| **약인공지능(ANI)** | 특정 작업에만 특화 (현재 수준) | 시리, 번역기, 챗봇 등 — 우리가 지금 쓰는 AI |
| **강인공지능(AGI)** | 인간과 동일한 수준의 사고 가능 | 아직 달성하지 못함 |
| **초인공지능(ASI)** | 인간을 뛰어넘는 기술적 특이점(**Singularity**) 도달 | SF 영화 수준 |

> **기술적 특이점(Singularity)이란?** AI가 인간의 지능을 초월하는 시점. 이후 AI가 스스로 더 뛰어난 AI를 만들어내는 "지능 폭발"이 일어날 수 있다는 가설이다. 시험에서 "특이점"이라는 용어가 나오면 초인공지능(ASI)과 연결.

> **3수준 구분 팁**: "한 가지만 잘하면 약(ANI), 뭐든지 잘하면 강(AGI), 인간을 넘으면 초(ASI)"

**⚠️ 시험 포인트**:
- AI ⊃ ML ⊃ DL 관계 출제됨
- 4가지 학습 종류 구분
- 10회 기출: "인공지능은 별도의 학습 없이도 문제에 대응할 수 있다" → **틀림** (학습 필수)
- 10회 기출: "사전 학습된 모델의 파라미터를 새 작업에 적용" → **전이 학습**

### 1.16 경량 딥러닝 학습 기법

**한 줄 요약**: 대기업의 거대 모델을 소규모 조직에서도 활용할 수 있게 해주는 기법들.

**왜 필요한가?** GPT 같은 거대 모델을 처음부터 만들려면 수십억 원이 드는데, 이미 만들어진 모델을 가져다 쓰면 비용을 대폭 절감할 수 있다. 이것이 바로 전이 학습이다.

| 기법 | 설명 | 비유 |
|------|------|------|
| **전이 학습 (Transfer Learning)** | 사전 훈련된 모델을 가져와 재사용 (**시험 출제됨**) | 영어 잘하는 사람이 스페인어를 빨리 배우는 것 |
| **파인튜닝 (Fine-tuning)** | 가져온 모델을 우리 상황에 맞게 재조정 | 기성복을 사서 수선하는 것 |
| **지식 증류 (Knowledge Distillation)** | 선생 네트워크 → 학생 네트워크로 지식 전달 (모델 경량화) | 대학교수가 핵심만 추려서 고등학생에게 가르치는 것 |

```
전이 학습의 흐름:

[구글이 만든 거대 모델]  ──가져옴──→  [우리 회사]  ──파인튜닝──→  [우리 상황에 맞는 모델]
   (수천억 원 투자)                   (비용 절감)                  (실무 적용)
```

**⚠️ 시험 포인트**:
- 전이 학습: "기존 모델 재사용" 키워드
- 파인튜닝: "미세 조정" 키워드
- 지식 증류: "선생 → 학생" 키워드
- 10회 기출: "사전 학습된 모델 파라미터를 그대로 사용하여 새 작업에 적용" → **전이 학습**

📝 보충: 최신 인공지능 기술 동향 (생성형 AI, LLM 등)도 시험에 나올 수 있으므로 관련 용어를 훑어볼 것.

### 1장 연습문제

**Q1. 다음 중 DIKW 피라미드에서 "지식(Knowledge)" 단계에 해당하는 것은?**
1. 오늘 아메리카노가 120잔 팔렸다
2. 아메리카노가 라떼보다 1.5배 많이 팔렸다
3. 오후 2시~4시에 원두를 미리 갈아놓으면 효율적이다
4. 직장인 대상 세트 메뉴를 개발하면 매출이 오를 것이다

> **정답: 3**
> 해설: (1)은 데이터(객관적 사실), (2)는 정보(패턴 인식), (3)은 지식(의사결정에 활용 가능한 예측), (4)는 지혜(창의적 전략 확장). "효율적이다"라는 판단이 포함되어 의사결정에 활용할 수 있으므로 지식이다. **왜 (4)가 지혜인가?** 기존 분석 결과를 새로운 영역(세트 메뉴 개발)으로 확장했기 때문.

**Q2. 다음 중 빅데이터 시대의 변화로 올바르지 않은 것은?**
1. 표본 조사 → 전수 조사
2. 사전 처리 → 사후 처리
3. 인과 관계 → 상관 관계
4. 데이터의 양 → 데이터의 질

> **정답: 4**
> 해설: 빅데이터 시대에는 데이터의 **질**보다 **양**을 중시하는 방향으로 변화했다(양→질이 아니라 질→양). "전후양상" 암기법 기억! (4)는 방향이 반대. **왜 나머지가 맞는가?** (1) 컴퓨팅 파워 증가로 전수 조사 가능, (2) 일단 모으고 나중에 처리, (3) 원인보다 패턴/연관성 발견이 중요해짐.

**Q3. 다음 중 빅데이터 조직의 "분산 구조"에 대한 설명으로 옳은 것은?**
1. 독립적 전담 빅데이터 조직을 별도로 구성한다
2. 각 부서에서 직접 데이터 사이언티스트를 양성한다
3. 분석 조직의 인력을 현업 부서에 파견하여 빠르게 적용/확산한다
4. 전사적 분석 표준화와 통합 관리에 가장 유리하다

> **정답: 3**
> 해설: (1)은 집중 구조 — 핵심 키워드 "독립적/별도". (2)는 기능 구조 — 핵심 키워드 "각 부서에서 직접 양성". (4)는 집중 구조의 장점 — "전사적 표준화"는 집중 구조에서 가능. 분산 구조는 분석 인력을 현업에 배치(파견)하여 빠르게 적용/확산하는 구조다. 10회 기출에서 집중형과 분산형을 혼동하게 하는 문제가 출제된 바 있다.

**Q4. (심화) 다음 사례에서 DIKW 피라미드의 각 단계를 올바르게 매칭한 것은?**

> 온라인 쇼핑몰에서:
> (가) 지난 달 반품률 12%
> (나) 의류 카테고리 반품률이 전자제품보다 3배 높다
> (다) 의류 구매 시 사이즈 가이드를 강화하면 반품을 줄일 수 있다
> (라) 사이즈 가이드뿐 아니라 AR 피팅 서비스를 도입하면 고객 경험을 혁신할 수 있다

1. (가)데이터 - (나)정보 - (다)지식 - (라)지혜
2. (가)정보 - (나)지식 - (다)지혜 - (라)데이터
3. (가)데이터 - (나)지식 - (다)정보 - (라)지혜
4. (가)정보 - (나)데이터 - (다)지식 - (라)지혜

> **정답: 1**
> 해설: (가) 12%라는 수치 = 객관적 사실(데이터). (나) 의류 vs 전자제품 비교 = 패턴 인식(정보). (다) "~하면 줄일 수 있다" = 의사결정(지식). (라) 새로운 영역(AR)으로 확장 = 창의적 전략(지혜). 핵심은 "비교하면 정보, 판단하면 지식, 확장하면 지혜".

## 2장: 개인정보 법제도

> **이전 장과의 연결**: 1장에서 빅데이터가 무엇인지, 어떤 특성(3V)을 가지는지 배웠다. 이제 2장에서는 그 빅데이터를 다룰 때 **법적으로 무엇이 가능하고, 무엇이 불가능한지**를 배운다. 아무리 좋은 데이터가 있어도 법을 모르면 활용할 수 없다.

### 2.1 데이터 3법

**한 줄 요약**: 개인정보를 보호하면서도 빅데이터 분석을 가능하게 하기 위해 개정된 3개 법률.

**왜 필요한가**: 빅데이터 분석에서 개인정보는 피할 수 없는 이슈다. 법을 모르면 실무에서 위법 행위를 하게 되고, 시험에서도 **정말 중요하게 출제**된다.

> 암기법: **"개정신"** (개인정보보호법, 정보통신망법, 신용정보법)

> 💡 **다른 장과의 연결**: 6장에서 배울 비식별화 기법(가명처리, 총계처리 등)과 프라이버시 보호 모델(K-익명성 등)은 모두 이 2장의 법적 테두리 안에서 운영된다. "왜 비식별화를 해야 하느냐?" → 이 법 때문이다.

**핵심 설명**:

데이터 3법 개정의 **가장 중요한 이유**: **가명정보** 개념 도입

기업이 고객 개인정보를 빅데이터 분석에 활용하고 싶지만, 그냥 쓰면 법 위반. 그렇다고 "쓰지 마"라고 하면 기업 경쟁력 저하. → 가명정보라는 중간 지대를 만듦.

그래서 실제로 어떻게 쓰이냐면... 병원이 환자 데이터로 신약 효과를 연구하고 싶다. 환자 이름/주민번호는 가명처리하고, 나이/성별/질병명만 남기면 → 가명정보로서 동의 없이 연구에 활용 가능.

#### 개인정보 → 가명정보 → 익명정보

```
┌──────────┐       ┌──────────┐       ┌──────────┐
│ 개인정보  │──────→│ 가명정보  │──────→│ 익명정보  │
│          │ 가명처리│          │ 익명처리│          │
│ 식별 가능 │       │추가정보   │       │절대 식별  │
│          │       │없이 불가  │       │불가      │
│동의 필요  │       │동의 없이  │       │자유롭게  │
│          │       │활용 가능  │       │활용 가능  │
└──────────┘       └──────────┘       └──────────┘
  보호 수준: 최고        중간              해당 없음
  활용 자유: 최저        중간              최고
```

| 구분 | 개인 식별 | 활용 조건 | 설명 | 예시 |
|------|----------|----------|------|------|
| **개인정보** | 가능 | 동의 필요 | 개인을 알아볼 수 있는 정보 | 홍길동, 010-1234-5678 |
| **가명정보** | 추가정보 없이 불가 | 동의 없이 활용 가능 (특정 목적 하) | 가명 처리하여 식별 불가하게 만든 정보 | 가나다, 서울/30대/남성 |
| **익명정보** | 절대 불가 | 제한 없이 자유롭게 활용 | 결합해도 알아볼 수 없는 정보 | 30대 남성 100명의 평균 소비 |

> **개인정보 vs 가명정보 구분 팁**: "이 데이터에 다른 정보를 결합하면 누군지 알 수 있나?" → Yes면 가명정보, No면 익명정보

**⚠️ 시험 포인트**:
- 10회 기출: "개인 정보 보호는 반드시 익명화되어야 한다" → **틀림** (익명화는 선택 가능한 방법일 뿐)
- 10회 기출: "직접 식별 불가하지만 다른 정보와 결합 시 특정 가능" → **가명정보**
- 10회 기출: "가능한 많은 개인 정보를 수집하여 분석에 활용" → **틀림** (최소 수집 원칙)

📝 보충: **개인정보보호법 / 정보통신망법 / 신용정보법 3법 핵심 차이**

| 구분 | 개인정보보호법 | 정보통신망법 | 신용정보법 |
|------|-------------|------------|----------|
| **관할** | 모든 분야 (일반법) | 정보통신(온라인) 분야 | 금융/신용 분야 |
| **주관 부처** | 개인정보보호위원회 | 방송통신위원회 | 금융위원회 |
| **대상** | 모든 개인정보처리자 | 정보통신서비스 제공자 | 신용정보회사, 금융기관 |
| **핵심 내용** | 개인정보 수집/이용/제공 전반 규율 | 온라인 개인정보 보호, 스팸 규제 | 신용정보 수집/이용/보호 |
| **개정 핵심** | 가명정보 개념 도입, 데이터 활용 기반 마련 | 개인정보 보호 규정을 개인정보보호법으로 이관 | 마이데이터(본인신용정보관리업) 도입 |

> **핵심 포인트**: 2020년 데이터 3법 개정으로 정보통신망법의 개인정보 관련 규정이 **개인정보보호법으로 이관**되었다. 즉, 개인정보보호법이 일반법으로서 중심 역할을 하게 됨.

> **현실 예시**: 
> - 네이버가 회원 정보를 수집할 때 → 개인정보보호법 + (과거) 정보통신망법
> - 카카오뱅크가 대출 심사용 데이터를 쓸 때 → 신용정보법
> - 병원이 환자 데이터를 연구에 쓸 때 → 개인정보보호법 (가명처리 후 활용)

### 2.2 개인정보 비식별 조치 가이드라인

**한 줄 요약**: 개인정보를 가명정보로 만드는 4단계 절차.

**왜 이 순서인가?** 먼저 개인정보인지 확인(사전 검토)하고 → 비식별 처리하고(비식별 조치) → 제대로 됐는지 검증하고(적정성 평가) → 계속 관리(사후 관리). 요리에 비유하면: 재료 확인 → 조리 → 맛 검사 → 보관 관리.

**절차**:

```
1. 사전 검토        2. 비식별 조치      3. 적정성 평가      4. 사후 관리
   ↓                   ↓                  ↓                 ↓
개인정보          가명처리, 총계처리    K-익명성, L-다양성   지속적인
해당 여부 확인    삭제, 마스킹 등      T-근접성으로 평가    모니터링
```

> 💡 **다른 장과의 연결**: 2단계의 비식별 조치 기법은 6.3절에서, 3단계의 적정성 평가 모델(K-익명성 등)은 6.4절에서 자세히 배운다.

### 2.2-1 GDPR (General Data Protection Regulation)

**한 줄 요약**: EU의 개인정보보호 일반규정으로, 전 세계에서 가장 강력한 개인정보보호법.

**왜 필요한가**: 데이터 3법이 한국 법이라면 GDPR은 글로벌 기준이다. EU 시민 데이터를 다루는 모든 기업에 적용되므로 빅데이터 실무에서 반드시 알아야 하며, 시험에서도 기본 개념이 출제된다.

**핵심 설명**:

비유하면 EU가 만든 "개인정보 헌법"이다. 2018년 5월 시행되었으며, 위반 시 전 세계 매출의 최대 4% 또는 2,000만 유로 중 높은 금액이 과징금으로 부과된다.

| 핵심 원칙 | 설명 | 비유 |
|----------|------|------|
| **정보 주체의 권리** | 개인이 자신의 데이터에 대해 접근, 정정, 삭제를 요구할 수 있음 | 내 물건은 내가 관리 |
| **잊힐 권리(Right to be Forgotten)** | 개인정보 삭제를 요구할 수 있는 권리 | 과거 기록을 지워달라고 요청 |
| **데이터 이동권(Data Portability)** | 자신의 데이터를 다른 서비스로 옮길 수 있는 권리 | 통신사 번호이동처럼 데이터도 이동 |
| **DPO 지정 의무** | 데이터 보호 책임자(Data Protection Officer) 지정 | 회사마다 개인정보 전담 관리자 |
| **Privacy by Design** | 서비스 설계 단계부터 개인정보보호를 내장 | 집 지을 때부터 방범 설계 |

**GDPR vs 한국 데이터 3법 비교**:

| 비교 항목 | GDPR | 한국 데이터 3법 |
|----------|------|---------------|
| 적용 범위 | EU 시민 데이터를 다루는 전 세계 기업 | 한국 내 기업 |
| 과징금 | 전 세계 매출 4% 또는 2,000만 유로 | 관련 매출액 3% 이하 |
| 잊힐 권리 | 명시적 보장 | 삭제 요구권 (유사) |
| DPO | 의무 지정 | 개인정보 보호책임자 의무 |

> 💡 **다른 장과의 연결**: 2.1절의 데이터 3법이 국내 규정이라면, GDPR은 해외 데이터를 활용하는 빅데이터 프로젝트에서 반드시 준수해야 할 글로벌 규정이다.

**⚠️ 시험 포인트**:
- "잊힐 권리"와 "데이터 이동권"은 GDPR의 대표 키워드
- GDPR은 2018년 시행, EU 규정
- 과징금이 매우 강력하다는 점이 특징 (전 세계 매출 4%)
- "Privacy by Design" = 설계 단계부터 개인정보보호 반영

### 2.3 빅데이터의 부작용과 통제 방안

**한 줄 요약**: 빅데이터 발전에 따른 프라이버시 침해, 책임 원칙 훼손 등의 부작용과 대응 방안.

| 위기 요인 | 사례 | 통제 방안 |
|----------|------|----------|
| **사생활 침해** | SNS 데이터가 사생활 침해 | 제공자가 아닌 **사용자에게 책임** 전환 (사용자가 함부로 쓰면 처벌 → 조심하게 됨 → 결과적으로 사생활 보호) |
| **책임 원칙 훼손** | 범죄 예측으로 아직 범죄 안 저지른 사람 체포 | **결과에 대해서만** 책임 부과 |
| **알고리즘 오용** | 분석 결과를 잘못 사용하여 피해 | 알고리즘 **해석 가능**하게 만들기 |

**알고리즈미스트(Algorithmist)**: 알고리즘을 해석하여 부당하게 피해 입은 사람들을 구제하는 전문 인력. 비유하면 "AI 변호사" — 알고리즘이 왜 이런 판단을 내렸는지 분석해서 억울한 사람을 도와주는 역할.

> **3가지 매칭 빠르게 외우기**:
> - **사생활** → **사**용자 책임 (사-사)
> - **책임** → **결**과에만 (책임은 결과로)
> - **알고리즘** → **해**석 가능 (알-해)

📝 보충: **빅데이터 위기요인과 통제방안 — 구체적 사례**

| 위기 요인 | 구체적 사례 | 통제 방안 상세 |
|----------|-----------|--------------|
| **사생활 침해** | 타겟(Target) 마트가 구매 데이터 분석으로 10대 소녀의 임신 사실을 아버지보다 먼저 알아냄 → 맞춤 쿠폰 발송으로 논란 | **동의 기반 수집 → 사용자 책임 전환**: 데이터 제공자가 아닌 활용자에게 책임. 옵트인(Opt-in) 방식으로 명시적 동의 확보 |
| **책임 원칙 훼손** | 미국 일부 지역에서 빅데이터 범죄 예측 시스템으로 "범죄를 저지를 확률이 높은 사람"을 사전 감시 → 아직 범죄를 저지르지 않은 사람의 인권 침해 | **예측이 아닌 결과에만 책임**: 행위가 발생한 후에만 책임을 물어야 함 |
| **알고리즘 오용** | 아마존 AI 채용 시스템이 여성 지원자에게 불이익을 주는 편향 발생 (과거 남성 중심 채용 데이터로 학습했기 때문) | **알고리즘 해석 가능성 확보**: 블랙박스 모델 지양, 설명 가능한 AI(XAI) 적용, 알고리즈미스트 활용 |

> **추가 통제 방안 키워드**: 기술적 통제(암호화, 접근 제어), 관리적 통제(정책, 교육), 법적 통제(법규 준수)

**⚠️ 시험 포인트**:
- 위기 요인과 통제 방안 매칭 문제
- **책임 원칙 훼손** = "아직 범죄를 저지르지 않았는데 체포" → 10회 기출에서 이 패턴으로 출제
- 10회 기출: "실제 신용도와 무관하게 불이익을 주는 사례" → 책임 원칙 위반

### 2장 연습문제

**Q1. 데이터 3법 개정의 가장 핵심적인 변화는?**
1. 모든 개인정보 수집을 금지하게 되었다
2. 가명정보 개념을 도입하여 동의 없이도 특정 목적 하에 활용할 수 있게 되었다
3. 익명정보만 빅데이터 분석에 사용할 수 있게 되었다
4. 개인정보보호법이 폐지되고 정보통신망법으로 통합되었다

> **정답: 2**
> 해설: 데이터 3법 개정의 핵심은 **가명정보** 개념 도입이다. (1)은 수집 자체를 금지한 것이 아님, (3)은 가명정보도 활용 가능, (4)는 반대로 정보통신망법의 개인정보 규정이 개인정보보호법으로 이관되었다. **왜 (3)이 틀린가?** 익명정보"만" 가능하다면 기업이 분석할 수 있는 데이터가 너무 적어진다. 가명정보까지 활용 가능하게 한 것이 핵심.

**Q2. 다음 중 빅데이터 위기 요인과 통제 방안의 연결이 올바른 것은?**
1. 사생활 침해 → 알고리즘을 해석 가능하게 만들기
2. 책임 원칙 훼손 → 데이터 제공자에게 책임 전환
3. 알고리즘 오용 → 결과에 대해서만 책임 부과
4. 책임 원칙 훼손 → 예측이 아닌 결과에 대해서만 책임 부과

> **정답: 4**
> 해설: 사생활 침해→사용자 책임 전환, 책임 원칙 훼손→결과에만 책임, 알고리즘 오용→해석 가능하게 만들기. (1)은 알고리즘 오용의 통제방안, (2)는 사생활 침해의 통제방안이지만 "제공자"가 아닌 "사용자"에게 책임 전환이므로 틀림, (3)은 책임 원칙 훼손의 통제방안이 아님. **왜 (2)가 교묘한 함정인가?** "제공자"와 "사용자"는 한 글자 차이지만 의미가 정반대다. 데이터를 제공한 사람이 아니라 활용하는 사람이 책임져야 한다.

**Q3. 개인정보 비식별 조치 절차를 올바른 순서로 나열한 것은?**
1. 비식별 조치 → 사전 검토 → 적정성 평가 → 사후 관리
2. 사전 검토 → 적정성 평가 → 비식별 조치 → 사후 관리
3. 사전 검토 → 비식별 조치 → 적정성 평가 → 사후 관리
4. 적정성 평가 → 사전 검토 → 비식별 조치 → 사후 관리

> **정답: 3**
> 해설: 사전 검토(개인정보 해당 여부) → 비식별 조치(가명처리 등 실시) → 적정성 평가(K-익명성 등으로 검증) → 사후 관리(모니터링) 순이다. 비식별 조치를 먼저 한 뒤에 평가하는 것이 핵심. **왜 (2)가 틀린가?** 적정성 평가는 비식별 조치를 한 "후에" 제대로 됐는지 검증하는 단계이므로, 조치 전에 할 수 없다.

**Q4. (심화) 다음 중 개인정보, 가명정보, 익명정보에 대한 설명으로 올바르지 않은 것은?**
1. 가명정보는 추가 정보 없이는 개인을 식별할 수 없다
2. 익명정보는 어떤 정보와 결합해도 개인을 식별할 수 없다
3. 가명정보는 통계 작성, 과학적 연구 등의 목적으로 동의 없이 활용할 수 있다
4. 가명정보는 개인정보보호법의 적용을 받지 않는다

> **정답: 4**
> 해설: 가명정보는 여전히 개인정보보호법의 적용을 받는다. 개인정보보호법 적용을 받지 않는 것은 **익명정보**다. 가명정보는 개인정보의 한 형태로, 특정 목적(통계, 연구, 공익적 기록 보존)에 한해 동의 없이 활용 가능하지만 여전히 법의 규제 대상이다.

## 3장: 데이터 분석 기획

> **이전 장과의 연결**: 2장에서 법적 테두리를 알았으니, 이제 그 안에서 **어떻게 분석을 기획할 것인가**를 배운다. 분석 대상(What)과 방법(How)을 정하고, 우선순위를 매기고, 프로젝트 계획을 세우는 단계다.

### 3.1 분석 방향성 도출 (분석 매트릭스)

**한 줄 요약**: 분석 대상과 방법을 알고 있는지에 따라 4가지로 분류한다.

> 💡 **다른 장과의 연결**: 이 매트릭스에서 "발견" 유형은 1장의 비지도 학습과 연결되고, "최적화" 유형은 4장의 CRISP-DM 방법론에서 체계적으로 실행된다. 분석 유형을 먼저 파악해야 적합한 방법론을 선택할 수 있다.

**핵심 설명**:

비유: 지금 배가 너무 고프다고 생각해 보자.

| 분석 유형 | 대상(What) | 방법(How) | 비유 |
|----------|-----------|----------|------|
| **발견** | 모름 | 모름 | 뭘 먹을지도 모르고, 요리법도 모름 |
| **솔루션** | 앎 | 모름 | 라면 먹고 싶은데, 끓이는 법 모름 |
| **통찰** | 모름 | 앎 | 요리는 잘하는데, 뭘 먹고 싶은지 모름 |
| **최적화** | 앎 | 앎 | 라면 먹고 싶고 끓일 줄도 앎 → 더 맛있게! |

📝 보충: **분석 매트릭스 2x2 그림**

```
              방법(How)
            모름         앎
          ┌───────────┬───────────┐
  대 모름 │  발견      │  통찰      │
  상      │ Discovery │ Insight   │
 (What)   ├───────────┼───────────┤
     앎   │  솔루션    │  최적화    │
          │ Solution  │ Optimize  │
          └───────────┴───────────┘
```

> **현실 기업 예시:**
> - **발견**: 매출이 떨어지는데 원인도 모르고, 어떻게 분석할지도 모름
> - **솔루션**: "고객 이탈"이 문제인 건 알겠는데, 분석 방법을 모름
> - **통찰**: 분석 기법은 아는데, 어떤 문제에 적용할지 모름 (데이터 사이언티스트가 현업에 투입된 경우)
> - **최적화**: 이미 추천 알고리즘이 있고, 정확도를 95%→98%로 올리고 싶음

> **외우는 팁**: 발견(둘 다 ?)→솔루션(What만 O)→통찰(How만 O)→최적화(둘 다 O). "발솔통최" 순서로, What을 먼저 알면 솔루션, How를 먼저 알면 통찰.

**⚠️ 시험 포인트**:
- 10회 기출: "통찰 — 분석 대상은 모르지만 방법은 알고 있는 경우" → **맞음**
- 10회 기출: "최적화 — 분석 대상과 방법을 모두 알고 있어야" → **맞음**
- 각 유형의 What/How 조합 정확히 암기

**시험 출제 예시**: "데이터 분석 전문가가 새로 입사했는데 분석 기법은 잘 알지만 회사의 어떤 문제를 분석할지 모르는 상황" → **통찰** (How=앎, What=모름)

### 3.2 분석 기획 접근 방식

**한 줄 요약**: 문제가 발생했을 때 빠르게 해결하는 과제 중심적 접근과, 근본 원인을 해결하는 장기적 마스터플랜 접근이 있다.

**핵심 설명**:

비유: 내가 식당 운영 중인 요리사인데, 고객이 "요리에 머리카락이 있어요!"라고 컴플레인을 건 상황.

| 접근 방식 | 과제 중심적 | 장기적 마스터플랜 |
|----------|-----------|----------------|
| **대응** | 빠르게 해결 | 근본 원인 파악 |
| **키워드** | Speed, Quick | Accuracy, Long-term |
| **초점** | 문제 해결 | 문제 정의 |
| **기간** | 단기 | 장기 |
| **비유** | 즉시 요리 다시 만들기 | 주방 시스템/교육 점검 |

| 과제 중심적 접근 4요소 | 장기적 마스터플랜 4요소 |
|---------------------|---------------------|
| Speed (빠르게) | Accuracy (정확하게) |
| Quick (신속하게) | Long-term (장기적으로) |
| Task-oriented (과제 중심) | Problem definition (문제 정의) |
| Problem solving (문제 해결) | Analytic (분석적) |

> **두 접근의 차이가 왜 중요한가?** 시험에서 키워드 하나로 "이것은 어떤 접근인가?"를 물어보기 때문. Speed/Quick이 보이면 과제 중심, Accuracy/Long-term이 보이면 마스터플랜.

**⚠️ 시험 포인트**:
- "과제 중심적 접근 방법이 아닌 것은?" → 장기적 마스터플랜의 요소(Accuracy 등)가 오답 보기

### 3.3 분석 기획 시 고려사항

**왜 필요한가?** 분석 프로젝트를 시작하기 전에 "할 수 있는지", "누가 해봤는지", "실패하면 어쩌지"를 점검하지 않으면 프로젝트가 중간에 좌초된다.

1. **가용 데이터 파악**: 필요한 데이터를 실제로 확보할 수 있는지 (없으면 분석 자체가 불가)
   - 예: "고객 이탈 분석을 하고 싶은데, 이탈 사유 데이터가 있나?" → 없으면 먼저 수집 체계부터 마련
2. **유스 케이스 탐색**: 비슷한 문제를 다른 기업이 어떻게 풀었는지 참조 (바퀴를 재발명하지 않기)
   - 예: "넷플릭스가 추천 시스템을 어떻게 만들었는지 참고하자"
3. **장애 대응 계획**: 데이터 품질 문제, 인력 이탈, 일정 지연 등 사전 대비
   - 예: "핵심 분석가가 퇴사하면?" → 문서화/백업 인력 확보

### 3.4 IT 프로젝트 우선순위 선정

**한 줄 요약**: 전략적 중요도(시급성)와 실행 용이성(난이도)을 기준으로 프로젝트 우선순위를 정한다.

**핵심 설명**:

#### IT 프로젝트 우선순위 (ISP 기준)

| 기준 | 질문 |
|------|------|
| **전략적 중요도** | 조직의 비전과 맞는가? |
| **시급성** | 해결이 지연되면 리스크가 있는가? |
| **실행 용이성** | 비용/기술적으로 실행 가능한가? |

#### 데이터 분석 프로젝트 우선순위

시급성(Value 관점)과 난이도(3V 관점)의 2x2 매트릭스.

> **왜 3V가 크면 난이도가 높은가?** 데이터 양이 방대하고(Volume), 형태가 다양하고(Variety), 실시간 처리가 필요할수록(Velocity) 분석이 어려워진다. 예: "고객 이탈 방지" 프로젝트에서 수억 건 거래 로그(Volume) + 통화/앱/SNS 비정형 데이터(Variety) + 실시간 감지(Velocity) → 3V 모두 높으므로 난이도 "어려움".

```
        시급함          시급하지 않음
       ┌──────────┬──────────┐
 쉬움  │  ① 먼저  │    ③     │
       ├──────────┼──────────┤
 어려움│    ②     │  ④ 나중  │
       └──────────┴──────────┘
```

- ① (쉽고 시급) → 무조건 먼저
- ④ (어렵고 안 시급) → 마지막
- 나머지는 기업의 가치관에 따라:
  - **시급성 중요시**: ③ → ④ → ② (미래 시급한 것을 현재로 당겨옴)
  - **난이도 중요시**: ③ → ① → ② (어려운 것을 쉬운 쪽으로 끌어내림)

> **주의**: "시급성이 중요하다 = 시급한 것부터"가 아니라, **"시급한 것을 현재로 조정해 오는 것"**이 핵심. 이것은 자격검정 기관의 해석 방식이므로 그대로 외울 것.

**⚠️ 시험 포인트**:
- 기출에서 실제로 출제됨. 순서 반드시 암기.
- 난이도 관점은 3V, 시급성 관점은 **Value** (3V에 포함 안 됨!)
- "난이도에 3V + Value 넣어서 틀린 것 고르기" 형태 출제

**시험 출제 예시**: "빅데이터 분석 프로젝트의 난이도 평가에 활용되는 3V에 해당하지 않는 것은?" → (1) Volume (2) Variety (3) Velocity (4) Value → **정답: 4** (Value는 시급성 관점)

### 3.4-1 분석 ROI (투자 대비 수익)

**한 줄 요약**: 분석 프로젝트가 투자 대비 얼마나 가치를 창출하는지 평가하는 지표.

**왜 필요한가**: 빅데이터 분석 기획 단계에서 "이 분석을 왜 해야 하는가"를 경영진에게 설득하려면 ROI로 정량적 기대 효과를 제시해야 한다. 시험에서 분석 기획의 경제성 평가 개념으로 출제된다.

**핵심 설명**:

비유하면 "100만원 투자해서 300만원 벌었으면 ROI는 200%"다.

```
ROI = (분석으로 얻은 이익 - 분석 투자 비용) / 분석 투자 비용 x 100%
```

| 구분 | 항목 | 예시 |
|------|------|------|
| **투자 비용** | 인프라, 인력, 도구, 데이터 구매 | 하둡 클러스터 구축비, 데이터 사이언티스트 인건비 |
| **기대 이익** | 매출 증가, 비용 절감, 리스크 감소 | 이탈 고객 예측으로 연 10억 매출 방어 |

**분석 ROI 산정이 어려운 이유**:
- 분석 효과가 **간접적**일 수 있음 (고객 만족도 향상 → 매출 증가의 인과관계 입증 어려움)
- **장기적** 효과를 단기 ROI로 측정하기 어려움
- **데이터 자체의 가치**를 금전으로 환산하기 어려움 (1.9절의 "빅데이터 가치 산정이 어려운 이유"와 연결)

> 💡 **다른 장과의 연결**: 1.9절에서 배운 "빅데이터 가치 산정이 어려운 이유"가 ROI 산정의 어려움과 직결된다. 3.4절의 우선순위 선정에서도 시급성(Value)이 곧 ROI가 높은 프로젝트를 의미한다.

**⚠️ 시험 포인트**:
- 분석 기획 시 경제성 분석(ROI)이 포함되어야 함
- ROI가 높은 프로젝트 = 시급성(Value) 높음 → 우선순위 높음
- 분석 ROI는 직접 효과(매출 증가)와 간접 효과(의사결정 개선)를 모두 고려

### 3.5 분석 문제 정의 — 하향식 접근법

**한 줄 요약**: 문제가 주어진 상태에서 위에서 아래로 내려가며 해답을 찾는 방법.

**절차**: 문제 탐색 → 문제 정의 → 해결 방안 탐색 → 타당성 검토

```
하향식 접근법 플로우:

  ┌──────────────────────────────────────┐
  │  1. 문제 탐색                         │
  │  "우리 회사에 어떤 문제가 있지?"        │
  │  도구: 비즈니스 모델 캔버스, STEEP      │
  └────────────┬─────────────────────────┘
               ↓
  ┌──────────────────────────────────────┐
  │  2. 문제 정의                         │
  │  "이 문제의 본질이 뭐지?"              │
  │  문제를 구체적/측정 가능하게 정의        │
  └────────────┬─────────────────────────┘
               ↓
  ┌──────────────────────────────────────┐
  │  3. 해결 방안 탐색                     │
  │  "어떻게 풀 수 있지?"                  │
  │  분석 기법/모델 검토                    │
  └────────────┬─────────────────────────┘
               ↓
  ┌──────────────────────────────────────┐
  │  4. 타당성 검토                        │
  │  "이 방안이 실현 가능한가?"             │
  │  경제적/기술적/운영적 타당성 평가        │
  └────────────────────────────────────────┘
```

#### 타당성 검토 3가지 관점

| 관점 | 질문 | 예시 |
|------|------|------|
| **경제적 타당성** | 투자 대비 수익이 있는가? (ROI) | "이 분석에 5천만원 투자하면 1억 절감 가능한가?" |
| **기술적 타당성** | 기술적으로 실현 가능한가? | "우리 인프라로 실시간 분석이 가능한가?" |
| **운영적 타당성** | 조직이 받아들일 수 있는가? | "현업 담당자가 분석 결과를 실제로 활용할 의지가 있는가?" |

> **왜 3가지 모두 봐야 하는가?** 기술적으로 가능해도 비용이 너무 크면(경제적 실패) 안 되고, 돈과 기술이 있어도 현업이 거부하면(운영적 실패) 무의미하다. 3가지 중 하나라도 탈락하면 프로젝트를 재검토해야 한다.

#### 문제 탐색 단계의 도구들

**1) 비즈니스 모델 캔버스 단순화 (5가지 영역)**

> 암기법: **"지원 인프라 업무 중에 고객이 제품을 규제와 감사했다"**

5가지 영역:
1. 지원 인프라 (업무)
2. 고객 (제품)
3. 규제와 감사

**2) 거시적 관점 — STEEP 분석**

> 글자 따기: **S**ocial, **T**echnology, **E**conomy, **E**nvironment, **P**olitics

그래서 실제로 어떻게 쓰이냐면... 배달앱 시장을 분석한다면:
- **S**(사회): 1인 가구 증가 → 배달 수요 증가
- **T**(기술): GPS/결제 기술 발전 → 실시간 추적 가능
- **E**(경제): 경기 침체 시 외식보다 배달 선호
- **E**(환경): 일회용 포장 환경 규제 강화
- **P**(정치): 플랫폼 노동자 보호 법안

**3) 기타 탐색 방법**:
- 경쟁자 확대 관점
- 시장 니즈 영역의 재해석
- 내부 자료 참조
- 외부 모델 벤치마킹
- 유스 케이스(과거 성공 사례) 활용

**4) 정성적 분석 기법**:
- **포커스 그룹 인터뷰(FGI)**: 소수 실무자/전문가 그룹이 모여 심층 토론. 비유하면 "전문가 브레인스토밍 모임". 설문조사(정량)와 달리 "왜?"를 깊이 파고든다.
- 일반 인터뷰, 설문 등

**⚠️ 시험 포인트**:
- 10회 기출: "FGI의 특징?" → "전문가/현업 실무자 그룹을 모아 심층적 토론을 진행하는 방법"
- STEEP 각 요소 구분
- 타당성 검토의 세부 내용도 시험 출제 가능

### 3.6 분석 문제 정의 — 상향식 접근법

**한 줄 요약**: 문제 정의가 어려울 때 아래에서 위로 사물을 그대로 인식하며 쌓아 올리는 방법.

**절차**: 프로세스 분류 → 프로세스 흐름 분석 → 분석 요건 시(試) → 분석 요건 정의

- **비지도 학습** 주로 활용 (정답을 모르는 상태에서 분석)
- **프로토타이핑 접근법** 활용: 시(試)모델을 먼저 만들어 보여주고, 점점 기능을 붙여 나감

📝 보충: **하향식 vs 상향식 접근법 비교 다이어그램**

```
  【하향식 (Top-Down)】              【상향식 (Bottom-Up)】

  문제 탐색 ← 문제가 주어짐          프로세스 분류
      ↓                                  ↓
  문제 정의                          프로세스 흐름 분석
      ↓                                  ↓
  해결 방안 탐색                     분석 요건 시(試)
      ↓                                  ↓
  타당성 검토                        분석 요건 정의 → 문제 발견!

  ▶ "위에서 아래로"                  ▶ "아래에서 위로"
  ▶ 문제 알 때 → 해답 찾기           ▶ 문제 모를 때 → 문제 찾기
  ▶ 지도 학습 성격                   ▶ 비지도 학습 성격
```

> **현실 예시:**
> - **하향식**: "고객 이탈률이 20%다. 왜 떠나는지 분석하자" → 원인 변수 탐색 → 예측 모델 구축
> - **상향식**: "우리 데이터로 뭘 할 수 있을까?" → 구매 데이터 탐색 → "아, 금요일 저녁에 피자+맥주 동시 구매가 많구나!" → 번들 상품 기획

> **하향식 vs 상향식 차이가 왜 중요한가?** 문제를 알고 있느냐 모르느냐에 따라 접근법이 달라지고, 시험에서 "이 상황은 하향식/상향식 중 어떤 접근인가?"를 물어보기 때문.

---

### 3.7 혼합 접근법과 디자인 싱킹

**한 줄 요약**: 상향식+하향식을 동시에 적용하는 방법.

- **발산 단계**: 상향식으로 가능한 방안들 도출
- **수렴 단계**: 하향식으로 도출된 방안들 분석

```
발산 (상향식)                    수렴 (하향식)
  아이디어 확장  →→→→→→→→→→→→  아이디어 선별
     ╱ │ ╲                          │
   A   B   C                     최적안
```

대표적 기법: **디자인 싱킹** — 사용자 공감으로부터 시작하여 아이디어 발산/수렴/피드백으로 발전

### 3장 연습문제

**Q1. 분석 매트릭스에서 "분석 대상(What)은 모르지만 분석 방법(How)은 알고 있는" 유형은?**
1. 발견(Discovery)
2. 솔루션(Solution)
3. 통찰(Insight)
4. 최적화(Optimization)

> **정답: 3**
> 해설: 통찰은 What=모름, How=앎. 데이터 사이언티스트가 분석 기법은 알지만 어떤 문제에 적용할지 모르는 상황. 발견은 둘 다 모름, 솔루션은 What=앎 How=모름, 최적화는 둘 다 앎. **왜 (2)가 아닌가?** 솔루션은 What을 알고 있다. "문제는 알겠는데 어떻게 풀지?"가 솔루션, "풀 수는 있는데 뭘 풀지?"가 통찰.

**Q2. "과제 중심적 접근 방법"의 특징으로 올바르지 않은 것은?**
1. Speed (빠르게 해결)
2. Quick (신속하게 대응)
3. Accuracy (정확하게 분석)
4. Task-oriented (과제 중심)

> **정답: 3**
> 해설: Accuracy는 "장기적 마스터플랜 접근"의 특징이다. 과제 중심적 접근은 Speed, Quick, Task-oriented, Problem solving이 핵심 키워드. 시험에서 둘을 섞어 놓는 함정 빈출! **구분법**: "빠르게/신속"이 느껴지면 과제 중심, "정확/장기/분석"이 느껴지면 마스터플랜.

**Q3. 하향식 접근법의 문제 탐색 단계에서 거시적 관점의 외부 환경 분석에 사용되는 기법은?**
1. SWOT 분석
2. STEEP 분석
3. 비즈니스 모델 캔버스
4. 포커스 그룹 인터뷰(FGI)

> **정답: 2**
> 해설: STEEP 분석은 Social, Technology, Economy, Environment, Politics의 약자로 **거시적 관점**의 외부 환경 분석 기법이다. SWOT은 별도의 전략 분석 프레임워크, 비즈니스 모델 캔버스는 문제 탐색의 내부 도구, FGI는 정성적 분석 기법. **왜 SWOT이 아닌가?** SWOT은 내부(강점/약점)+외부(기회/위협)를 종합하는 프레임워크이지만, "거시적 외부 환경"만 물어보면 STEEP이 정답.

**Q4. (심화) 다음 상황에서 가장 적합한 분석 유형은?**

> 신입 데이터 사이언티스트가 입사했다. 머신러닝, 통계 분석 역량은 뛰어나지만, 회사의 비즈니스 프로세스와 어떤 문제를 분석해야 하는지는 아직 모른다.

1. 발견
2. 솔루션
3. 통찰
4. 최적화

> **정답: 3**
> 해설: "분석 방법(How)은 앎 + 분석 대상(What)은 모름" = 통찰. 발견은 둘 다 모르는 경우이고, 솔루션은 문제를 알지만 방법을 모르는 경우. 이런 실무 시나리오를 매트릭스에 매핑하는 문제가 출제될 수 있다.

## 4장: 데이터 분석 방법론

### 4.1 분석 방법론 구성 요소

**한 줄 요약**: 분석 방법론에는 절차, 방법, 도구/기법, 템플릿/산출물이 있다.

비유: 냉면을 만든다면 → 요리 순서(절차), 요리법(방법), 냄비/칼(도구/기법), 완성된 냉면(산출물)

그래서 실제로 어떻게 쓰이냐면... "고객 이탈 예측 모델"을 만든다면:
- **절차**: 데이터 수집 → 전처리 → 모델링 → 평가 → 배포
- **방법**: 지도 학습(분류 모델)
- **도구/기법**: Python, scikit-learn, XGBoost
- **산출물**: 이탈 확률 예측 모델, 분석 보고서

---

### 4.2 분석 모델의 유형

| 모델 | 특징 | 핵심 키워드 | 비유 | 적합한 상황 |
|------|------|-----------|------|-----------|
| **계층적 프로세스 모델** | 단계 → 태스크 → 스텝의 계층 구조 | 빅데이터 분석 방법론의 기반 | 교과서 → 챕터 → 절 | 대규모 분석 프로젝트 |
| **폭포수 모델** | 위→아래, 이전 단계 완료 후 다음 진행 | 중간 이슈 시 치명적 | 폭포에서 떨어지면 다시 올라갈 수 없음 | 요구사항이 명확하고 변경 없을 때 |
| **프로토타입 모델** | 시(試)모델 먼저 만들고 보완 | 일부분 먼저 개발 | 베타 버전 앱을 먼저 출시하고 사용자 피드백 받아 개선 | 요구사항이 불명확할 때 |
| **나선형 모델** | 나선처럼 돌면서 점진적 완성 | **위험 요소 제거**에 초점 | 달팽이 껍데기처럼 점점 커짐 | 위험이 큰 대규모 프로젝트 |
| **애자일(Agile) 기법** | 짧은 주기(스프린트)로 피드백 반복 | 짧은 개발 주기, 지속적 피드백 | 2주마다 결과물 보여주고 수정 | 변경이 잦고 빠른 대응 필요할 때 |

> **이 비교가 왜 중요한가?** 시험에서 "위험 관리에 가장 적합한 모델은?" → 나선형, "요구사항 변경이 잦은 환경에 적합한 모델은?" → 애자일처럼 **상황에 맞는 모델을 고르는 문제**가 나온다. 핵심 키워드만 외우면 구분 가능.

```
각 모델의 핵심 차이:

폭포수:    ■ → ■ → ■ → ■ → ■  (일방통행, 되돌아감 불가)
프로토타입: ■ → [시제품] → 피드백 → ■ → [개선품] → 피드백
나선형:    ┌─→ ■ ─→ ■ ─┐
           │   (위험 분석) │  점점 확대
           └── ■ ←── ■ ─┘
애자일:    [스프린트1] [스프린트2] [스프린트3]  (짧은 주기 반복)
```

> **시험 팁**: "위험 제거"라는 키워드가 보이면 나선형, "되돌아갈 수 없다"면 폭포수, "짧은 주기/스프린트"면 애자일.

### 4.3 KDD 분석 방법론

**한 줄 요약**: Knowledge Discovery in Databases — 데이터 속에서 "쓸 만한 지식"을 캐내는 5단계 프로세스.

**왜 필요한가?**
금광에서 금을 캐려면 "어디를 팔지 → 흙을 걸러내고 → 금 모양으로 다듬고 → 실제로 캐내고 → 진짜 금인지 확인"하는 과정이 필요하다. KDD는 데이터에서 지식을 캐내는 이 과정을 체계화한 것이다.

> 💡 **다른 장과의 연결**: KDD의 "데이터 선택→전처리→변환→마이닝→해석"은 1장의 DIKW에서 D(데이터)를 K(지식)으로 끌어올리는 구체적 절차다.

**절차 (5단계)**:

```
데이터 선택 → 전처리 → 변환 → 데이터 마이닝 → 해석/평가
  (1)         (2)      (3)       (4)           (5)
```

| 단계 | 하는 일 | 비유 |
|------|---------|------|
| **데이터 선택** | 분석 대상 데이터를 골라냄 | 금광에서 팔 구역 선정 |
| **전처리** | 결측값, 이상치 제거/정제 | 흙과 돌을 걸러냄 |
| **변환** | 분석에 적합한 형태로 변환 (정규화, 파생변수 등) | 원석을 가공 가능한 크기로 자름 |
| **데이터 마이닝** | 패턴/규칙 발견 (분류, 군집, 연관분석 등) | 실제로 금을 캐냄 |
| **해석/평가** | 발견한 패턴이 유의미한지 검증 | 진짜 금인지 감정 |

> **"데이터 마이닝"이란?** 말 그대로 "데이터 광산에서 캐기(Mining)". 대량의 데이터 속에서 숨겨진 패턴, 규칙, 관계를 자동으로 찾아내는 기술이다. 분류, 군집, 연관분석 등이 여기 해당한다. 비유하면 모래사장에서 금 가루를 체로 걸러내는 것.

**⚠️ 시험 포인트**:
- KDD는 **5단계**, CRISP-DM은 **6단계** — 단계 수 구분 주의
- KDD에서 "데이터 마이닝"은 5단계 중 **4번째** 단계 (전체가 데이터 마이닝이 아님!)

---

### 4.4 CRISP-DM 분석 방법론

**한 줄 요약**: 가장 대표적인 데이터 분석 방법론. 시험에 가장 자주 출제된다.

> 암기법: **"업데데이트 모델 평가전"** (업무 이해 → 데이터 이해 → 데이터 준비 → 모델링 → 평가 → 전개)
> (업데이트 하는데 렉 한 번 걸려서 "데"가 두 번!)

| 순서 | 단계 | 핵심 활동 | 현실 예시 (이커머스 이탈 예측) |
|------|------|----------|---------------------------|
| 1 | **업무 이해** | 비즈니스 목표 이해 | "고객 이탈률 30%를 20%로 낮추자" |
| 2 | **데이터 이해** | 데이터 수집, 탐색 | 구매 이력, 접속 로그, 고객 정보 확인 |
| 3 | **데이터 준비** | 전처리, 변환 | 결측값 처리, 파생변수 생성 |
| 4 | **모델링** | 모델 작성 및 **모델 평가** | 랜덤포레스트로 이탈 예측 모델 구축 |
| 5 | **평가** | 분석 결과 평가, 모델링 과정 평가, 모델 적용성 평가 | "이 모델을 실무에 쓸 수 있나?" 검토 |
| 6 | **전개** | 실제 현장에 적용 | CRM 시스템에 모델 연동, 이탈 위험 고객에 쿠폰 발송 |

📝 보충: **CRISP-DM 순환 플로우 다이어그램**

```
           ┌──────────┐
     ┌────→│ 업무 이해 │←────────────────────┐
     │     └────┬─────┘                      │
     │          ↓                            │
     │     ┌──────────┐                      │
     │     │데이터 이해│                      │ (실패 시 되돌아감)
     │     └────┬─────┘                      │
     │          ↓                            │
     │     ┌──────────┐                      │
     │     │데이터 준비│←──┐                  │
     │     └────┬─────┘   │ (반복)           │
     │          ↓         │                  │
     │     ┌──────────┐   │                  │
     │     │  모델링   │──┘                   │
     │     └────┬─────┘                      │
     │          ↓                            │
     │     ┌──────────┐                      │
     │     │   평가    │──────────────────────┘
     │     └────┬─────┘
     │          ↓
     │     ┌──────────┐
     └─────│   전개    │
           └──────────┘
```

> **핵심**: "데이터 준비 ↔ 모델링"은 서로 반복하고, "평가"에서 실패하면 "업무 이해"로 되돌아갈 수 있다. 일방통행이 아닌 **순환 구조**! 이것이 폭포수 모델과의 결정적 차이다.
>
> **순서 주의**: 반드시 **"데이터 이해" → "데이터 준비"** 순서다. 데이터가 뭐가 있는지 먼저 파악(이해)한 다음에야 전처리/변환(준비)을 할 수 있다. 시험에서 이 순서를 뒤집어 놓는 함정이 나온다.

**⚠️ 시험 포인트 — 핵심 함정**:
- **모델 작성 및 평가**는 "모델링" 단계에서 수행 (평가 단계가 아님!)
- "평가"라는 단어가 들어갔다고 "평가 단계"로 착각하면 틀림
- 평가 → 전개로 넘어갈 때 **실패가 발생하면 "업무 이해" 단계로 다시 돌아갈 수 있다**
- 순서 문제가 가장 많이 출제됨

> **"모델링 단계의 평가" vs "평가 단계"를 확실히 구분하는 비유**:
> - **모델링 단계의 평가** = 요리사가 요리하면서 **중간에 간을 보는 것** (맛이 부족하면 소금 추가 → 모델 조정)
> - **평가 단계** = 요리가 다 끝난 후 **메뉴로 내도 되는지 총괄 심사하는 것** (이 요리가 식당 전체 메뉴에 올라갈 만한가? → 프로젝트 전체를 되돌아보는 단계)

**시험 출제 예시**: "CRISP-DM에서 모델의 성능을 테스트하고 조정하는 활동은 어떤 단계에서 수행되는가?" → **모델링 단계** ("평가 단계"로 낚시하는 것이 핵심 함정)

---

### 4.5 기타 분석 방법론

- **SEMMA**: SAS 통계 프로그램 업체에서 만든 방법론 (앞글자를 딴 것). 시험 출제된 적이 없지만 존재를 알아둘 것.
  - **S**ample(표본 추출) → **E**xplore(탐색) → **M**odify(수정) → **M**odel(모델링) → **A**ssess(평가)

> **SEMMA가 KDD/CRISP-DM과 다른 점**: SEMMA는 "업무 이해"나 "전개" 단계가 없다. 순수하게 **데이터 분석 과정만** 다루며, SAS 도구 사용을 전제로 한다. 따라서 실무 적용까지 고려하는 CRISP-DM보다 범위가 좁다.

📝 보충: **KDD vs CRISP-DM vs SEMMA 단계 비교**

```
KDD          CRISP-DM        SEMMA
─────────    ─────────────   ──────────
             업무 이해        
데이터 선택  데이터 이해      Sample(표본추출)
전처리       데이터 준비      Explore(탐색)
변환                         Modify(수정)
데이터마이닝 모델링           Model(모델링)
해석/평가    평가             Assess(평가)
             전개             
```

| 비교 항목 | KDD | CRISP-DM | SEMMA |
|----------|-----|----------|-------|
| 개발 주체 | 학계 (Fayyad) | 유럽 컨소시엄 | SAS사 |
| 단계 수 | 5단계 | 6단계 | 5단계 |
| 핵심 특징 | 데이터 마이닝에 초점 | 업무 이해부터 전개까지 | 통계 분석 도구 중심 |
| 순환 구조 | X (순차적) | O (되돌아감 가능) | X (순차적) |
| 시험 빈출 | 중 | **최다 출제** | 거의 안 나옴 |

📝 보충: **CRISP-DM vs 빅데이터 분석 방법론(계층적 프로세스 모델) 단계 대응표**

| CRISP-DM (6단계) | 빅데이터 분석 방법론 (5단계) | 핵심 활동 |
|------------------|--------------------------|----------|
| 업무 이해 | **분석 기획** | 비즈니스 목표 파악, 분석 계획 수립 |
| 데이터 이해 + 데이터 준비 | **데이터 준비** | 데이터 탐색/수집/전처리를 하나로 |
| 모델링 | **데이터 분석** | 모델 구축 및 분석 수행 |
| (해당 없음) | **시스템 구현** | 분석 결과를 실제 시스템에 반영 |
| 평가 + 전개 | **평가 및 전개** | 결과 평가 후 현장 적용 |

> **차이점 핵심**: CRISP-DM은 "데이터 이해"와 "데이터 준비"를 분리하지만, 빅데이터 분석 방법론은 이를 하나로 묶는다. 또한 빅데이터 분석 방법론에는 "시스템 구현" 단계가 별도로 존재한다.

> **비교표에서 이 차이가 왜 중요한가?** 시험에서 "CRISP-DM과 KDD의 차이"를 물어볼 수 있다. 결정적 차이: (1) 단계 수 (5 vs 6), (2) 순환 구조 여부, (3) CRISP-DM은 "업무 이해"와 "전개"가 추가됨 = 실무 적용까지 고려.

> **현실 예시**: 은행에서 대출 부실 예측 모델을 만든다면?
> - **KDD 관점**: 과거 대출 데이터 선택 → 결측치 제거 → 변수 변환 → 분류 모델 적용 → 결과 해석
> - **CRISP-DM 관점**: "왜 부실이 발생하는가?" 업무 이해부터 시작 → 데이터 탐색 → 전처리 → 모델링 → 평가 → 실제 심사 시스템에 적용(전개)

### 4.6 빅데이터 분석 방법론

**한 줄 요약**: **계층적 프로세스 모델(단계→태스크→스텝)** 기반의 빅데이터 전용 방법론. **시험에 무조건 나온다.**

> 암기법: 단계 순서 — **(💡 2025ver)** **"PPADD"** = **P**lanning(분석기획), **P**reparation(데이터준비), **A**nalysis(데이터분석), **D**evelopment(시스템구현), **D**eployment(평가및전개)
> ⚠️ 참고: 마지막 단계 영문은 Deployment(전개)이지만, 한글 교재에서는 "평가 및 전개"로 평가 활동을 포함하여 명명. 시험에서는 **한글 명칭 "평가 및 전개"**가 출제된다.

| 순서 | 단계 | 주요 활동 | 현실 예시 |
|------|------|----------|----------|
| 1 | **분석 기획** | 비즈니스 이해, 범위 설정(SOW), 프로젝트 정의/계획(WBS), 위험 계획 | "추천 시스템 만들 거야. 범위는 여기까지." |
| 2 | **데이터 준비** | 데이터 수집, 정제, 변환 | 구매 데이터 수집, 결측값 정리 |
| 3 | **데이터 분석** | 탐색적 데이터 분석(EDA), 모델링 | 데이터 시각화 후 모델 구축 |
| 4 | **시스템 구현** | 시스템 개발, 테스트 | 모델을 API로 만들어 서비스에 연동 |
| 5 | **평가 및 전개** | 결과 평가, 실제 적용 | A/B 테스트 후 전체 적용 |

```
빅데이터 분석 방법론의 계층 구조:

  단계 (Phase)     ← 가장 큰 단위 (5개)
    ├── 태스크 (Task)    ← 중간 단위
    │     ├── 스텝 (Step)    ← 가장 작은 단위
    │     └── 스텝
    └── 태스크
          └── 스텝

예시: "분석 기획"(단계) → "위험 계획 수립"(태스크) → "위험 식별"(스텝)
```

#### 분석 기획 단계 세부 사항

- **SOW (Statement of Work)**: 비즈니스 이해 및 범위 설정 시 작성하는 문서. 비유하면 "이번 프로젝트에서 뭘 하고 뭘 안 할지" 정하는 계약서.
- **WBS (Work Breakdown Structure)**: 프로젝트 정의 및 계획 수립 시 작성하는 문서. 비유하면 "할 일 목록을 트리 구조로 쪼갠 것". 큰 작업을 작은 작업으로 분해.

```
WBS 예시:

  추천 시스템 프로젝트
  ├── 1. 데이터 수집
  │     ├── 1.1 구매 데이터 추출
  │     ├── 1.2 클릭 로그 수집
  │     └── 1.3 고객 정보 연동
  ├── 2. 모델 개발
  │     ├── 2.1 협업 필터링 구현
  │     └── 2.2 콘텐츠 기반 필터링 구현
  └── 3. 시스템 배포
        ├── 3.1 API 개발
        └── 3.2 A/B 테스트
```

**위험 계획 수립 4가지 기법**:

> 암기법: **"회전완수"**

| 기법 | 설명 | 비유 | 현실 예시 |
|------|------|------|----------|
| **회피** | 위험을 피해 버림 | 그냥 피해 버려! | 위험한 기술 대신 안전한 기술 선택 |
| **전이** | 다른 부서/상급자에게 넘김 | 남한테 넘겨! | 보험 가입(위험을 보험사에 전이) |
| **완화** | 돈/자원을 투자하여 완화 | 돈으로 해결! | 테스트 서버 추가 구매 |
| **수용** | 그냥 받아들임 | 감수한다! | "일정 지연은 발생할 수 있다" 인정 |

> **4가지 기법의 차이 포인트**: 회피는 "안 한다", 전이는 "남에게 맡긴다", 완화는 "영향을 줄인다", 수용은 "그냥 감수한다". 시험에서 사례를 주고 어떤 기법인지 물어본다.

#### 탐색적 데이터 분석 (EDA)

데이터를 본격 분석하기 전에, 분석할 데이터의 특성을 사전에 파악하는 과정:
- **기초 통계**: 평균, 분산 등으로 파악
- **시각화**: 그래프로 데이터 특성 파악

비유하면 요리 전에 재료의 상태를 확인하는 것 — "이 재료 신선한가? 양은 충분한가?"

**⚠️ 시험 포인트**:
- 각 단계의 순서와 세부 태스크 모두 중요
- WBS → "프로젝트 수행 계획 수립 단계에서 작성" (10회 기출)
- 10회 기출: "데이터 분석 프로젝트 수행 순서?" → 비즈니스 이해 → 프로젝트 정의 → 수행 계획 수립 → 위험 계획 수립
- "회전완수" 위험 대응 4가지 기법 암기 필수
- **(💡 2025ver 보충)** 세부 내용까지 모두 공부해야 함. 시험 문제 무조건 나온다.

### 4.7 분석 과제 고려 요소

**한 줄 요약**: 데이터 크기, 속도, 복잡도, 분석 복잡도, 정확도/정밀도 5가지를 고려해야 한다.

#### 정확도 vs 정밀도 (트레이드오프)

| 개념 | 여기서의 의미 | 4과목에서의 의미 | 비유 |
|------|-------------|----------------|------|
| **정확도** | 모델이 얼마나 틀리지 않느냐 | 혼동행렬의 평가 지표 | 과녁 중앙에 얼마나 가까운가 |
| **정밀도** | 여러 번 반복했을 때 동일한 결과가 나오느냐 | 혼동행렬의 평가 지표 | 여러 번 쏠 때 화살이 한 곳에 모이는가 |

```
정확도 높음 + 정밀도 높음     정확도 높음 + 정밀도 낮음
      ◎                          ○  ·
     ·◎                         ·  ○
      ◎·                       ○   ·
   (이상적!)                  (가끔 맞지만 일관성 없음)

정확도 낮음 + 정밀도 높음     정확도 낮음 + 정밀도 낮음
                    · ·                ·
                   · ·            ·       ·
                    ·               ·   ·
   (일관되지만 빗나감)         (최악)
```

> **주의**: 여기서 말하는 정확도/정밀도는 **과녁 비유**(정확=중심에 가까움, 정밀=모여 있음)의 일반적 개념이다. 4과목에서 혼동행렬(Confusion Matrix)과 함께 나오는 정밀도(Precision)/재현율(Recall)과는 **완전히 다른 맥락**이므로, 지금은 과녁 비유만 기억하면 된다. 혼동행렬은 4과목에서 본격적으로 배운다.

### 4.8 프로젝트 관리 지식 체계 (PMBOK)

**한 줄 요약**: 프로젝트 관리자가 갖추어야 할 10가지 영역.

> 암기법 (2026ver): **"범총이 의자에서 시원한 조리품 먹었다"**
> 암기법 (2025ver): **"이범통이 의자에서 시원한 조리품 먹었다"**

| 번호 | 영역 | 암기 키워드 |
|------|------|-----------|
| 1 | 범위 관리 | 범 |
| 2 | 총합(통합) 관리 | 총(통) |
| 3 | 이해관계자 관리 | 이 |
| 4 | 의사소통 관리 | 의 |
| 5 | 자원 관리 | 자 |
| 6 | 시간(일정) 관리 | 시 |
| 7 | 원가(비용) 관리 | 원 |
| 8 | 조달 관리 | 조 |
| 9 | 리스크 관리 | 리 |
| 10 | 품질 관리 | 품 |

📝 보충: **PMBOK 10대 지식영역 각각의 한 줄 설명**

| 영역 | 한 줄 설명 | 현실 예시 |
|------|-----------|----------|
| **범위 관리** | 프로젝트에서 "무엇을 할 것인가"를 정의하고 통제 | "이번 프로젝트에서 추천 시스템만 만든다, 챗봇은 제외" |
| **통합 관리** | 전체 프로젝트의 계획/실행/변경을 총괄 조정 | 프로젝트 매니저가 전체 진행 상황 조율 |
| **이해관계자 관리** | 프로젝트에 영향을 미치는 사람들을 식별/관리 | 경영진, 현업 팀장, 고객 등의 요구 사항 조율 |
| **의사소통 관리** | 프로젝트 정보의 생성/배포/관리 계획 | 주간 보고 체계, 회의록 관리 |
| **자원 관리** | 인적/물적 자원의 확보와 배분 | 데이터 분석가 3명 배정, 서버 확보 |
| **시간(일정) 관리** | 프로젝트 일정 수립 및 진도 관리 | 간트 차트로 마일스톤 관리 |
| **원가(비용) 관리** | 예산 편성과 비용 통제 | 총 예산 2억 원 내 집행 |
| **조달 관리** | 외부 자원/서비스 구매(아웃소싱) 관리 | 클라우드 서버 임대 계약 |
| **리스크 관리** | 위험 요인 식별/분석/대응 계획 수립 | "데이터 확보 실패 시" 대안 마련 |
| **품질 관리** | 프로젝트 산출물의 품질 기준 충족 보장 | 모델 정확도 90% 이상 달성 여부 점검 |

> **10대 영역의 구조적 이해**: 핵심 3개 — **범위(무엇을)-시간(언제까지)-비용(얼마로)** — 가 "프로젝트 삼각형(Triple Constraint)"이다. 이 3개가 서로 트레이드오프 관계(범위 늘리면 시간/비용 증가)이고, 나머지 7개(통합/이해관계자/의사소통/자원/조달/리스크/품질)는 이 삼각형을 **지원하는 역할**이다. 통합 관리가 전체를 총괄 조정한다.
>
> **PMBOK과 다른 개념의 연결**: 4.6절의 "위험 계획 수립(회전완수)"는 PMBOK의 "리스크 관리"와 연결된다. WBS는 "범위 관리"와 연결된다.

**⚠️ 시험 포인트**:
- "다음 중 PMBOK 10가지 영역이 아닌 것은?" 형태
- (💡 2025ver 보충) "아웃소싱이 지식 체계의 어느 영역에 속하느냐?"로 출제된 적 있음 → **조달 관리**

### 4장 연습문제

**Q1. CRISP-DM에서 "모델 작성 및 평가"가 수행되는 단계는?**
1. 데이터 준비 단계
2. 모델링 단계
3. 평가 단계
4. 전개 단계

> **정답: 2**
> 해설: CRISP-DM 최대 함정! "모델 작성 및 **평가**"라는 말에 속아 "평가 단계"를 고르면 틀린다. 모델 자체의 작성과 평가는 **모델링 단계**에서 수행한다. "평가 단계"는 분석 결과 전체에 대한 평가. **왜 이게 함정인가?** "평가"라는 단어 때문에 반사적으로 3번을 고르게 되지만, 모델링 단계 안에서 모델을 만들고 테스트하는 것은 모델링의 일부다. 5번째 "평가 단계"는 모델뿐 아니라 분석 전체 과정을 되돌아보는 단계.

**Q2. 빅데이터 분석 방법론의 위험 계획 수립에서, 위험을 다른 부서/상급자에게 넘기는 기법은?**
1. 회피
2. 전이
3. 완화
4. 수용

> **정답: 2**
> 해설: "회전완수"에서 전이 = 다른 곳에 넘김. 회피는 피해버림, 완화는 돈/자원으로 줄임, 수용은 감수. 보험에 가입하는 것도 전이의 예시(위험을 보험사에 넘김). **왜 (1)이 아닌가?** 회피는 위험 자체를 "피하는" 것(위험한 작업을 안 하기로 결정), 전이는 위험을 "다른 곳에 맡기는" 것(작업은 하되 책임을 넘김).

**Q3. 다음 중 빅데이터 분석 방법론(계층적 프로세스 모델)의 단계 순서로 올바른 것은?**
1. 데이터 준비 → 분석 기획 → 데이터 분석 → 시스템 구현 → 평가 및 전개
2. 분석 기획 → 데이터 분석 → 데이터 준비 → 시스템 구현 → 평가 및 전개
3. 분석 기획 → 데이터 준비 → 데이터 분석 → 시스템 구현 → 평가 및 전개
4. 분석 기획 → 데이터 준비 → 시스템 구현 → 데이터 분석 → 평가 및 전개

> **정답: 3**
> 해설: 분석 기획 → 데이터 준비 → 데이터 분석 → 시스템 구현 → 평가 및 전개. 기획이 먼저, 데이터를 준비한 뒤 분석, 그 결과를 시스템으로 구현, 최종 평가 및 전개. **왜 (2)가 틀린가?** 데이터 분석 전에 데이터 준비가 먼저 되어야 한다. 재료(데이터) 없이 요리(분석)할 수 없다.

**Q4. (심화) 다음 중 KDD와 CRISP-DM의 차이점에 대한 설명으로 올바르지 않은 것은?**
1. KDD는 5단계, CRISP-DM은 6단계이다
2. CRISP-DM은 "업무 이해" 단계가 KDD에는 없다
3. CRISP-DM은 순환 구조이고 KDD는 순차적이다
4. KDD의 "데이터 마이닝" 단계는 CRISP-DM의 "평가" 단계에 대응한다

> **정답: 4**
> 해설: KDD의 "데이터 마이닝"은 CRISP-DM의 **"모델링"** 단계에 대응한다 (둘 다 실제 분석/패턴 발견을 수행). "평가"가 아님. (1) KDD 5단계, CRISP-DM 6단계 — 맞음. (2) CRISP-DM은 "업무 이해"로 시작하지만 KDD는 바로 "데이터 선택"부터 — 맞음. (3) CRISP-DM은 되돌아갈 수 있는 순환 구조 — 맞음.

## 5장: 분석 거버넌스와 수준 진단

> **이전 장과의 연결**: 3~4장에서 분석 기획 방법과 방법론(CRISP-DM, KDD 등)을 배웠다. 이제 5장에서는 **우리 조직이 그런 분석을 할 준비가 되어 있는지** 진단한다. 아무리 좋은 방법론을 알아도 조직이 준비 안 되어 있으면 실행할 수 없기 때문이다.

### 5.1 분석 거버넌스 체계

**한 줄 요약**: 기업이 데이터 분석을 체계적으로 수행하기 위한 관리 체계.

> 암기법: **"시조프로 마인드 대"** (시스템, 조직, 프로세스, 마인드 육성, 데이터)

**왜 필요한가?** 개인이 아닌 **조직 전체**가 데이터 분석을 잘하려면 시스템도 필요하고, 조직 구성도 필요하고, 프로세스도 정해야 한다. 한 마디로 "분석을 잘하기 위한 회사 차원의 규칙과 인프라".

그래서 실제로 어떻게 쓰이냐면... 삼성전자가 AI 기반 불량 탐지를 도입한다면: 분석 플랫폼(시스템) 구축, AI팀(조직) 구성, 분석 표준 절차(프로세스) 수립, 분석용 데이터(데이터) 관리 체계 마련, 전 직원 데이터 리터러시 교육(마인드 육성)이 모두 필요하다.

**구성 요소** (왜 이 5가지인가: 사람 없으면 안 되고, 도구 없으면 안 되고, 절차 없으면 혼란):

```
분석 거버넌스 5대 구성 요소:

  ┌────────┐    ┌────────┐    ┌──────────┐
  │ 시스템  │────│  조직   │────│ 프로세스  │
  │(도구)  │    │(사람)  │    │(절차)    │
  └────┬───┘    └────┬───┘    └─────┬────┘
       │             │              │
       └──────┬──────┘──────┬───────┘
              │             │
       ┌──────┴───┐  ┌──────┴────┐
       │  데이터   │  │ 마인드 육성 │
       │(원재료)  │  │(교육)     │
       └──────────┘  └───────────┘
```

1. **시스템**: 분석 도구/플랫폼 구축 (없으면 분석 자체 불가)
2. **조직**: 전담 분석 조직 구성 (누가 할지 정해야)
3. **프로세스**: 분석 절차 표준화 (매번 다르게 하면 품질 불균일)
4. **데이터**: 분석용 데이터 관리 체계 (쓰레기 데이터로는 좋은 결과 불가)
5. **마인드 육성(교육)**: 전 직원의 데이터 리터러시 향상 (도구가 있어도 쓸 줄 모르면 무의미)

**⚠️ 시험 포인트**: 시험에 가끔 출제됨. 5가지 구성 요소 암기.

📝 보충: **데이터 거버넌스 7대 원칙** (시험 출제 가능)

| 번호 | 원칙 | 설명 | 왜 필요한가? |
|------|------|------|-------------|
| 1 | **책임성(Accountability)** | 데이터에 대한 명확한 책임자 지정 | 아무도 책임 안 지면 데이터가 방치됨 |
| 2 | **표준화(Standardization)** | 데이터 정의, 형식, 규칙의 표준 수립 | 부서마다 다른 형식이면 통합 불가 |
| 3 | **투명성(Transparency)** | 데이터 관련 의사결정 과정을 투명하게 공개 | 불투명하면 신뢰 상실 |
| 4 | **무결성(Integrity)** | 데이터의 정확성과 일관성을 보장 | 부정확한 데이터로 분석하면 잘못된 결론 |
| 5 | **감사 가능성(Auditability)** | 데이터 변경 이력을 추적/감사할 수 있어야 함 | 문제 발생 시 원인 추적 가능 |
| 6 | **보안성(Security)** | 데이터에 대한 접근 통제 및 보안 유지 | 개인정보 유출 방지 |
| 7 | **준거성(Compliance)** | 법규 및 규정을 준수 | 2장에서 배운 데이터 3법 등 준수 필수 |

> 암기법: **"책표투무감보준"** — 책임지고 표준을 투명하게 무결한 감사로 보안 준수!

> 💡 **다른 장과의 연결**: 이 7대 원칙 중 "보안성"과 "준거성"은 2장의 개인정보 법제도와 직접 연결된다. 데이터 거버넌스가 잘 갖춰져야 법을 준수하면서 분석할 수 있다.

### 5.2 분석 준비도

**한 줄 요약**: 우리 기업이 데이터 분석을 얼마나 준비했는지 6가지 분야로 진단.

> 암기법: **"IT 문대기 인파"**

**왜 이 6가지인가?** 분석을 하려면 인프라(IT), 문화, 데이터, 기법, 인력/조직, 업무 파악이 모두 갖춰져야 한다. 하나라도 빠지면 분석이 제대로 안 된다.

| 분야 | 설명 | 왜 필요한가? | "이게 없으면?" |
|------|------|-------------|--------------|
| **분석 업무 파악** | 어떤 분석 업무가 있는지 | 뭘 분석할지 모르면 시작 불가 | "뭘 해야 하지?" 상태 |
| **인력 및 조직** | 분석 인력/조직이 있는지 | 사람이 없으면 분석 불가 | "누가 하지?" 상태 |
| **분석 기법** | 어떤 기법을 쓸 수 있는지 | 방법을 모르면 분석 불가 | "어떻게 하지?" 상태 |
| **분석 데이터** | 분석할 데이터가 있는지 | 데이터가 없으면 분석 대상 없음 | "뭘 가지고 하지?" 상태 |
| **분석 문화** | 데이터 기반 의사결정 문화가 있는지 | 문화가 없으면 결과가 무시됨 | "분석했는데 아무도 안 봐" |
| **IT 인프라** | 빅데이터 분석 환경이 갖춰졌는지 | 도구가 없으면 실행 불가 | "뭘로 하지?" 상태 |

그래서 실제로 어떻게 쓰이냐면... 중소기업이 빅데이터 분석을 시작하려 할 때, 이 6가지 체크리스트로 "우리가 뭐가 부족한지" 진단한다. 인력은 있는데 IT 인프라가 없다? → 클라우드 도입부터. 인프라는 있는데 분석 문화가 없다? → 경영진 설득과 교육부터.

**⚠️ 시험 포인트**:
- 쉬운 문제: "분석 준비도 6가지 분야가 아닌 것은?"
- 어려운 문제: 각 분야의 세부 내용까지 물어봄
- 세부 내용은 눈에 익혀두면 "빅데이터 분석 환경 → IT 인프라" 같은 느낌으로 구분 가능

### 5.3 분석 성숙도

**한 줄 요약**: 우리 기업의 분석 수준이 얼마나 성숙했는지 CMMI 모델 기반으로 진단.

**CMMI(Capability Maturity Model Integration)**: 국제 표준 성숙도 모형. 시험에서 "CMMI"가 나오면 분석 성숙도를 물어보는 것. 비유하면 "기업의 분석 능력 등급표".

**3가지 부문**: 비즈니스 부문, 조직 및 역량 부문, IT 부문

**성숙도 단계 (낮→높)**:

> 암기법: **"도활확최"** (도입 → 활용 → 확산 → 최적화)

📝 보충: **분석 성숙도 계단식 다이어그램**

```
                                    ┌─────────┐
                                    │ 최적화   │ ← 전사 분석 최적화, 지속 혁신
                              ┌─────┤ (Lv.4)  │
                              │     └─────────┘
                        ┌─────┤
                        │     │  ┌─────────┐
                        │     └──│  확산    │ ← 전사적 분석 활용, 조직 확산
                  ┌─────┤        │ (Lv.3)  │
                  │     │        └─────────┘
                  │     │  ┌─────────┐
                  │     └──│  활용    │ ← 부서별 분석 활용 시작
            ┌─────┤        │ (Lv.2)  │
            │     │        └─────────┘
            │     │  ┌─────────┐
            │     └──│  도입    │ ← 분석 시작, 환경 구축
            │        │ (Lv.1)  │
            │        └─────────┘
     ───────┘
     성숙도 ↑
```

**각 단계에서 구체적으로 뭘 하는가?**

| 단계 | 상태 | 기업이 하는 일 |
|------|------|-------------|
| **도입** | 분석 시작 단계 | 분석팀 신설, 기본 환경 구축, 소수 프로젝트 시범 운영 |
| **활용** | 부서별 활용 시작 | 특정 부서에서 분석 적용, 반복 가능한 프로세스 정립 |
| **확산** | 전사적 확대 | 전 부서로 확산, 분석 표준화, 데이터 거버넌스 도입 |
| **최적화** | 지속적 혁신 | AI/자동화 적용, 실시간 의사결정, 분석 문화 정착 |

> **현실 예시**: 쿠팡의 분석 성숙도 진화 (가상 시나리오)
> - **도입**: 처음 데이터 분석팀 구성, 기본 리포트 작성
> - **활용**: 물류팀에서 배송 시간 예측 모델 적용
> - **확산**: 전 부서(마케팅, CS, 구매)에서 데이터 기반 의사결정
> - **최적화**: AI 추천 시스템이 매출의 35%를 견인, 지속적 개선

**⚠️ 시험 포인트**:
- "분석 성숙도의 부문이 아닌 것은?" → "비용" 같은 오답
- 단계 순서: 도입 → 활용 → 확산 → 최적화
- CMMI = 분석 성숙도 연상

### 5.4 준비도-성숙도 매트릭스

**한 줄 요약**: 준비도와 성숙도를 교차하여 기업의 분석 수준 유형을 진단.

> 암기법: 사분면 시계 방향으로 **"도준정확"**

```
           성숙도 높음
              │
    정착형    │   확산형 ← 가장 높은 수준
  ────────────┼────────────
    도입형    │   준비형
              │
           성숙도 낮음
   준비도 낮음        준비도 높음
```

| 유형 | 준비도 | 성숙도 | 설명 | 비유 |
|------|--------|--------|------|------|
| **도입형** | 낮음 | 낮음 | 시작 단계 | 막 운전면허 딴 초보 |
| **준비형** | 높음 | 낮음 | 준비는 됐지만 아직 성숙 안 됨 | 장비는 다 샀는데 아직 초보 |
| **정착형** | 낮음 | 높음 | 성숙했지만 새로운 준비 부족 | 운전은 잘하는데 차가 낡음 |
| **확산형** | 높음 | 높음 | 가장 수준 높음. 6가지 구성 요소 모두 갖추고 지속적 확산 가능 | 최신 차에 베테랑 운전자 |

> **도준정확 매트릭스가 왜 중요한가?** 기업의 현재 위치를 진단하고 "어디로 가야 하는가"를 알려주기 때문. 궁극적 목표는 **확산형**에 도달하는 것.

**⚠️ 시험 포인트**:
- "준비도 낮고 성숙도 높은 것은?" → 정착형
- 가장 수준 높은 것 = 확산형
- "도준정확" 시계 방향 암기

**시험 출제 예시**: "분석 인프라와 데이터는 충분히 확보했지만, 실제 분석 프로젝트 경험이 부족한 기업" → **준비형** (준비도 높음 + 성숙도 낮음)

### 5.5 데이터 거버넌스

**한 줄 요약**: 전사 차원에서 데이터에 대한 표준화된 관리 체계.

**왜 필요한가?** 데이터가 부서마다 다른 형식이면 통합 분석이 불가하고, 누가 책임지는지 모르면 품질이 떨어지고, 표준 절차가 없으면 매번 다르게 관리된다. 비유하면 "교통법규 없이 도로를 운영하면 사고가 나는 것"과 같다.

**구성 요소**: 

> 암기법: **"원조프로"** (원칙, 조직, 프로세스)

| 구성 요소 | 설명 | 현실 예시 |
|----------|------|----------|
| **원칙** | 데이터 관리의 기본 규칙/정책 | "개인정보는 반드시 암호화하여 저장한다" |
| **조직** | 데이터 관리 담당 조직/역할 | 데이터 스튜어드(데이터 관리자) 지정 |
| **프로세스** | 데이터 관리 절차/방법 | 데이터 입력 → 검증 → 승인 → 저장 절차 |

**주요 관리 대상**: 마스터 데이터, 메타데이터, 데이터 사전

그래서 실제로 어떻게 쓰이냐면... "고객"이라는 데이터를 마케팅팀은 "client", 영업팀은 "customer", 물류팀은 "buyer"로 부르면 통합 분석이 안 된다. 데이터 거버넌스가 "고객 = customer로 통일"이라는 표준을 정하면 해결된다.

#### 마스터 데이터 관리 (MDM: Master Data Management)

**한 줄 요약**: 기업 전체에서 공통으로 사용하는 핵심 데이터를 일관되게 관리하는 체계.

**왜 필요한가**: 고객, 제품, 조직 같은 핵심 데이터가 부서마다 다르면 분석 결과가 틀어진다. 빅데이터 분석의 기초가 되는 데이터 품질을 확보하려면 MDM이 필수다.

**핵심 설명**:

비유하면 "전 국민이 사용하는 주민등록번호 체계"와 같다. 각 부서가 고객을 다른 코드로 관리하면 통합이 불가능하지만, MDM으로 하나의 고객 코드 체계를 만들면 모든 부서가 같은 기준으로 데이터를 활용할 수 있다.

| 마스터 데이터 종류 | 설명 | 예시 |
|------------------|------|------|
| **고객 마스터** | 고객에 대한 기본 정보 | 고객ID, 이름, 연락처, 등급 |
| **제품 마스터** | 상품/서비스에 대한 기본 정보 | 제품코드, 제품명, 카테고리, 가격 |
| **조직 마스터** | 조직 구조에 대한 기본 정보 | 부서코드, 부서명, 상위조직 |

**MDM의 핵심 활동**:
- **단일화(Single View)**: 여러 시스템의 고객 정보를 하나의 통합 뷰로
- **표준화**: 데이터 형식, 코드 체계 통일
- **품질 관리**: 중복 제거, 최신 상태 유지
- **변경 관리**: 마스터 데이터 변경 시 승인 절차 적용

> **마스터 데이터 vs 트랜잭션 데이터**: 마스터 데이터는 "고객 정보"처럼 잘 안 변하는 참조 데이터, 트랜잭션 데이터는 "주문 내역"처럼 매일 쌓이는 거래 데이터. 마스터 데이터가 틀리면 트랜잭션 데이터 분석도 틀어진다.

**⚠️ 시험 포인트**:
- 마스터 데이터 = 기업 전사에서 공통 사용하는 핵심 참조 데이터
- MDM의 목적 = 데이터 일관성, 정확성, 단일화
- 데이터 거버넌스의 주요 관리 대상 중 하나

#### 메타데이터의 3가지 유형

**한 줄 요약**: 메타데이터는 기술 메타데이터, 관리 메타데이터, 비즈니스 메타데이터로 분류된다.

**왜 필요한가**: 1.4절에서 "메타데이터 = 데이터를 설명하는 데이터"라고 배웠다. 시험에서는 한 걸음 더 나아가 메타데이터의 3가지 유형을 구분하는 문제가 출제된다.

**핵심 설명**:

비유하면 도서관 책 한 권의 메타데이터를 3가지 관점에서 보는 것이다:

| 유형 | 설명 | 비유 (도서관) | 예시 |
|------|------|-------------|------|
| **기술 메타데이터** | 데이터의 물리적/기술적 구조 정보 | 책의 크기, 쪽수, ISBN | 테이블명, 컬럼명, 데이터 타입, 저장 위치, 파일 크기 |
| **관리 메타데이터** | 데이터의 관리/운영에 필요한 정보 | 대출 이력, 관리 담당자, 입고일 | 데이터 소유자, 접근 권한, 생성일, 변경 이력, 보존 기간 |
| **비즈니스 메타데이터** | 데이터의 업무적 의미/맥락 | 책의 주제 분류, 요약, 키워드 | 데이터 정의(업무 용어), 업무 규칙, 산출 공식, 관련 부서 |

> 암기법: **"기관비"** — 기술, 관리, 비즈니스. "기관비(기관의 비용)"로 외우면 된다.

**⚠️ 시험 포인트**:
- 3유형 이름과 예시 매칭 문제 출제
- "테이블명, 컬럼 타입"은 기술 메타데이터
- "데이터 소유자, 접근 권한"은 관리 메타데이터
- "업무 정의, 산출 공식"은 비즈니스 메타데이터

**데이터 거버넌스 체계**: 표준화, 저장소 관리, 관리 체계, 표준화 활동

**빅데이터 거버넌스** = 데이터 거버넌스 + 빅데이터 관련 요소 (효율적 관리, 최적화, 정보보호, 외부 데이터 통합 관리 등)

> **데이터 거버넌스 vs 분석 거버넌스 차이**: 데이터 거버넌스는 "데이터 자체를 어떻게 관리할 것인가"에 초점, 분석 거버넌스는 "분석 활동을 어떻게 체계화할 것인가"에 초점. 데이터 거버넌스는 분석 거버넌스의 하위 요소 중 하나.

```
분석 거버넌스와 데이터 거버넌스의 관계:

┌────────────────────────────────────┐
│         분석 거버넌스                │  ← "분석을 잘하기 위한 전체 체계"
│  ┌──────────────────────────────┐  │
│  │  시스템 │ 조직 │ 프로세스    │  │
│  ├──────────────────────────────┤  │
│  │  마인드 육성                  │  │
│  ├──────────────────────────────┤  │
│  │  ┌────────────────────────┐  │  │
│  │  │    데이터 거버넌스       │  │  │  ← "데이터 관리 체계" (하위 요소)
│  │  │  원칙 │ 조직 │ 프로세스 │  │  │
│  │  └────────────────────────┘  │  │
│  └──────────────────────────────┘  │
└────────────────────────────────────┘
```

**⚠️ 시험 포인트**: 시험에 자주 출제됨. 구성 요소/관리 대상/체계 구분.

(💡 2025ver 보충) 분석 지원 인프라 방안 수립 시 **플랫폼 구조**로 적용. 중앙 집중적으로 관리.

### 5장 연습문제

**Q1. 분석 준비도-성숙도 매트릭스에서 "준비도는 높지만 성숙도가 낮은" 유형은?**
1. 도입형
2. 준비형
3. 정착형
4. 확산형

> **정답: 2**
> 해설: 준비형 = 준비도 높음 + 성숙도 낮음. "준비는 다 됐는데 아직 실제로 잘 못하는 상태." 도입형은 둘 다 낮음, 정착형은 준비도 낮음+성숙도 높음, 확산형은 둘 다 높음. "도준정확" 시계방향 암기! **왜 (3)이 아닌가?** 정착형은 반대로 "성숙도는 높지만 준비도가 낮음" — 오래 분석해왔지만 새로운 도구/인프라 준비가 부족한 상태.

**Q2. 분석 성숙도 모델의 기반이 되는 국제 표준 모형은?**
1. PMBOK
2. CRISP-DM
3. CMMI
4. ISO 27001

> **정답: 3**
> 해설: CMMI(Capability Maturity Model Integration)가 분석 성숙도의 기반 모형이다. PMBOK은 프로젝트 관리 지식체계, CRISP-DM은 분석 방법론, ISO 27001은 정보보안 관리 표준. **구분 팁**: CMMI의 "Maturity"를 기억하면 성숙도와 바로 연결된다.

**Q3. 다음 중 데이터 거버넌스의 구성 요소가 아닌 것은?**
1. 원칙
2. 조직
3. 프로세스
4. 예산

> **정답: 4**
> 해설: 데이터 거버넌스의 구성 요소는 "원조프로"(원칙, 조직, 프로세스). 예산은 프로젝트 관리(PMBOK)의 원가 관리 영역에 해당하며, 데이터 거버넌스의 구성 요소가 아니다. **왜 예산이 아닌가?** 데이터 거버넌스는 "어떻게 관리할 것인가"의 체계이지, "얼마의 돈이 드는가"의 문제가 아니다.

**Q4. (심화) A 기업은 5년간 데이터 분석을 수행해 왔고 분석 전문 인력도 보유하고 있지만, 분석 플랫폼이 노후화되고 최신 빅데이터 도구를 갖추지 못했다. 이 기업은 준비도-성숙도 매트릭스에서 어떤 유형에 해당하는가?**
1. 도입형
2. 준비형
3. 정착형
4. 확산형

> **정답: 3**
> 해설: 5년간 분석 수행 = 성숙도 높음. 하지만 최신 도구/인프라 부족 = 준비도 낮음. 성숙도 높음 + 준비도 낮음 = 정착형. **준비형과 헷갈릴 수 있는데**: 준비형은 "장비는 좋은데 경험이 없는" 반대 상황이다.

## 6장: 데이터 수집 및 저장 계획

> **이전 장과의 연결**: 5장에서 우리 조직의 분석 준비도를 진단했다. 이제 6장에서는 **실제로 데이터를 어떻게 수집하고 저장하는지**, 구체적인 기술(ETL, HDFS, 크롤링 등)을 배운다. 분석의 원재료인 데이터를 모으는 단계다.

### 6.1 데이터 수집 기술

**한 줄 요약**: 데이터를 외부/내부에서 모아오는 다양한 기술들.

#### ETL (Extract, Transform, Load)

> **정말 중요하다.** 가장 대표적인 데이터 수집/적재 기술.

비유하면 해외 직구와 같다:
- **E(Extract)**: 해외 쇼핑몰에서 물건을 꺼냄 (배송 대행지에 보냄)
- **T(Transform)**: 한국 규격에 맞게 변환 (전압 변환, 한글 라벨 부착)
- **L(Load)**: 우리 창고(DB)에 입고

| 단계 | 영어 | 의미 | 현실 예시 |
|------|------|------|----------|
| **추출(E)** | Extract | 특정 소스에서 데이터를 꺼냄 | 각 부서 DB에서 데이터 추출 |
| **변환(T)** | Transform | 우리 기업에 맞게 데이터를 변환 | 날짜 형식 통일, 단위 변환 |
| **적재(L)** | Load | 변환된 데이터를 DB에 저장 | 데이터 웨어하우스에 적재 |

```
ETL 플로우:

[부서A DB]──┐
[부서B DB]──┼──[E: 추출]──→[T: 변환]──→[L: 적재]──→[데이터 웨어하우스]
[외부 데이터]┘
              꺼냄           맞춤             저장
```

> 💡 **다른 장과의 연결**: ETL의 결과물이 6.11절에서 배울 데이터 웨어하우스에 저장된다. 즉 ETL은 DW의 "입구"다.

#### 기타 수집 기술

| 기술 | 용도 | 비유 |
|------|------|------|
| **크롤링** | 웹 문서 수집 | 인터넷을 돌아다니며 페이지를 수집하는 로봇 |
| **스크래핑** | 웹 페이지 데이터 추출 | 수집한 페이지에서 필요한 정보만 뽑아내기 |
| **FTP** | **파일 전송** 프로토콜 (웹서버 로그가 아님!) | 택배로 파일을 보내는 것 |
| **Open API** | 실시간 데이터 교환 (중계소 같은 개념) | 앱이 날씨 정보를 기상청에서 실시간으로 가져오는 것 |
| **아파치 스쿱(Sqoop)** | RDBMS ↔ 하둡 간 데이터 전송 | 기존 DB와 하둡 사이의 택배기사 |
| **아파치 플럼(Flume)** | 로그 데이터 수집 | 실시간으로 흘러오는 로그를 모으는 수도관 |

> **크롤링 vs 스크래핑 차이**: 크롤링 = "웹 페이지를 수집" (문서 전체를 가져옴), 스크래핑 = "웹 페이지에서 데이터를 추출" (필요한 부분만 뽑음). 크롤링이 더 넓은 개념.

#### Open API를 통한 데이터 수집

**한 줄 요약**: 외부 기관이 제공하는 표준화된 인터페이스를 통해 실시간으로 데이터를 교환하는 방식.

**왜 필요한가**: 빅데이터 분석에서 외부 데이터(날씨, 교통, 공공데이터 등)를 수집할 때 가장 체계적인 방법이 API다. 크롤링/스크래핑과의 차이를 이해해야 한다.

**핵심 설명**:

비유하면 API는 **"식당 메뉴판과 주문 시스템"**이다. 손님(요청자)이 메뉴판(API 명세서)을 보고 주문(요청)하면, 주방(서버)이 음식(데이터)을 만들어 전달한다. 직접 주방에 들어가서 재료를 뒤지는 것(크롤링)과는 다르다.

| 구분 | API 수집 | 크롤링/스크래핑 |
|------|---------|---------------|
| **방식** | 제공자가 정한 규격에 따라 요청/응답 | 웹 페이지를 직접 방문하여 추출 |
| **데이터 형식** | JSON, XML 등 구조화된 형태 | HTML을 파싱해야 함 |
| **안정성** | 제공자가 보장 (버전 관리) | 웹 구조 변경 시 깨질 수 있음 |
| **법적 리스크** | 낮음 (허가된 접근) | 높을 수 있음 (이용약관 위반 가능) |
| **실시간성** | 실시간 데이터 교환 가능 | 주기적 수집 |

**API 동작 흐름**:
```
[요청자(클라이언트)]  ──요청(Request)──→  [API 서버(제공자)]
        │                                      │
        │            ←──응답(Response)──        │
        │           (JSON/XML 데이터)           │
```

**대표적인 Open API 사례**: 공공데이터포털(data.go.kr), 기상청 날씨 API, 카카오맵 API, 네이버 검색 API

> **REST API**: 현재 가장 널리 쓰이는 API 방식. HTTP 프로토콜(GET, POST 등)을 사용하며, URL로 자원을 식별한다. 예: `GET /api/weather?city=seoul` → 서울 날씨 데이터 반환.

**⚠️ 시험 포인트**:
- API = 실시간 데이터 교환, 표준화된 인터페이스
- 크롤링과 달리 **제공자가 허가한** 방식으로 데이터를 수집
- Open API는 공공데이터 활용의 핵심 수단
- JSON, XML 형식으로 데이터를 주고받음 (반정형 데이터와 연결)

**⚠️ 시험 포인트**:
- 10회 기출: "FTP — 웹서버 로그 수집" → **틀림** (FTP는 파일 전송 프로토콜)
- 10회 기출: "크롤링 — 웹 문서" → 맞음
- 10회 기출: "스크래핑 — 웹 페이지" → 맞음

### 6.2 데이터의 유형

#### 형태에 따른 분류

| 유형 | 특징 | 예시 | 저장소 | 비유 |
|------|------|------|--------|------|
| **정형 데이터** | 고정된 스키마(틀)가 있음 | RDBMS, 엑셀, CSV | 관계형 DBMS | 빈칸이 딱딱 정해진 신청서 |
| **반정형 데이터** | 스키마 없지만 **메타데이터(설명서)** 포함 | XML, JSON, HTML | - | 태그로 구분된 블로그 글 |
| **비정형 데이터** | 틀이 전혀 없는 자유 형태 | 텍스트, 이미지, 영상, 음원 | NoSQL | 자유롭게 쓴 일기장 |

```
정형 데이터 예시:          반정형 데이터 예시:        비정형 데이터 예시:
┌────┬────┬────┐         <person>                  "오늘 날씨가
│이름│나이│주소│           <name>홍길동</name>         정말 좋아서
├────┼────┼────┤           <age>25</age>              산책을 했다"
│홍  │ 25 │서울│         </person>                   
└────┴────┴────┘         (태그로 구조 표현)           (구조 없음)
(딱 정해진 틀)
```

**⚠️ 시험 포인트**:
- 반정형 데이터가 가장 중요! "메타데이터를 포함한다"가 핵심
- 10회 기출: "반정형 데이터는 태그값을 통해 의미 분석이 가능하다" → 맞음
- 10회 기출: "반정형 데이터는 구조 변경이 어렵다" → **틀림** (태그로 구조 변경 가능)
- 10회 기출: "정형 데이터는 고정된 스키마를 갖는다" → 맞음

**시험 출제 예시**: "다음 중 반정형 데이터의 특징으로 올바르지 않은 것은?" → "고정된 스키마를 가진다"가 정답 (반정형은 스키마가 없고 태그로 구조를 표현)

#### 표현 방식에 따른 분류

| 유형 | 설명 | 예시 |
|------|------|------|
| **정량적 데이터** | 수치로 표현 가능 | 매출액, 키, 몸무게, 온도 |
| **정성적 데이터** | 수치로 표현하기 어려운 질적 데이터 | 고객 만족도("매우 좋음"), 브랜드 이미지 |

#### 분석 목적에 따른 분류

```
데이터
├── 수치형 (회귀 분석에 활용)
│   ├── 연속형 (키, 몸무게, 온도 — 소수점 가능)
│   └── 이산형 (학생 수, 주문 건수 — 정수만)
└── 범주형 (분류 분석에 활용)
    ├── 명목형 (성별, 혈액형 — 순서 없음)
    └── 순서형 (학점, 만족도 등급 — 순서 있음)
```

> **수치형 vs 범주형 구분 팁**: "평균을 구할 수 있나?" → Yes면 수치형, No면 범주형. 혈액형의 평균은 무의미하므로 범주형.

(💡 2025ver 보충) **데이터의 척도**:

| 척도 | 구분 | 특징 | 예시 | 가능 연산 |
|------|------|------|------|----------|
| **명목 척도** | 질적 | 집단 분류 | 성별, 대학교 | 분류만 |
| **서열(순서) 척도** | 질적 | 서열 관계 존재 | 등수, 순위 | 대소 비교 |
| **등간(구간) 척도** | 양적 | 구간 간격에 의미 | 온도 | 덧셈/뺄셈만 |
| **비율 척도** | 양적 | 절대적 기준(0) 존재 | 무게, 나이 | 사칙연산 모두 |

> 온도: "어제보다 5도 높다"(O), "어제보다 2배 높다"(X) → 등간 척도
> 무게: "A가 B보다 2배 무겁다"(O) → 비율 척도 (0kg이 절대적 기준)

```
척도의 계층 구조 (위로 갈수록 더 많은 연산 가능):

  비율 척도  ← 사칙연산 모두 (무게, 나이)
    ↑
  등간 척도  ← 덧셈/뺄셈 (온도)
    ↑
  서열 척도  ← 대소 비교 (등수)
    ↑
  명목 척도  ← 분류만 (성별)
```

기타: 가역 데이터/비가역 데이터, 내부 데이터/외부 데이터도 한 번 읽어볼 것.

### 6.3 개인정보 비식별화 기법

**한 줄 요약**: 개인정보를 가명정보로 바꾸기 위한 5가지 기법.

> 💡 **다른 장과의 연결**: 2장에서 배운 "가명정보" 개념을 실현하는 구체적 기술이 여기에 있다. 2장 = "왜" 비식별화해야 하는지(법), 6장 = "어떻게" 비식별화하는지(기법).

**왜 5가지나 있는가?** 데이터의 종류와 활용 목적에 따라 적합한 기법이 다르기 때문이다. 이름은 대체(가명)하고, 통계 목적이면 집계(총계)하고, 불필요하면 지우고(삭제), 일부만 가리고(마스킹), 세부를 뭉개면(범주화) 된다. 실무에서는 보통 여러 기법을 **조합**하여 사용한다.

| 기법 | 설명 | 예시 | 핵심 키워드 |
|------|------|------|-----------|
| **가명 처리** | 다른 값으로 대체 | 홍길동 → 임꺽정 | "대체" |
| **총계 처리** | 집계된 수치만 제공 | 개인 성적 → 평균 점수 | "집계" |
| **삭제** | 식별 가능 정보 삭제 | 주민번호 삭제 | "제거" |
| **데이터 마스킹** | 일부를 가림 | 010-****-1234 | "가림" |
| **범주화** | 범주로 변환 | 23세 → 20대 | "범위화" |

> 암기법: **"가총삭마범"** (가명, 총계, 삭제, 마스킹, 범주화)

```
비식별화 5대 기법 적용 예시:

원본: 홍길동, 28세, 서울 강남구, 010-1234-5678, 연봉 5200만원

가명 처리: 임꺽정, 28세, 서울 강남구, 010-1234-5678, 연봉 5200만원
총계 처리: (개인 정보 대신) 평균 나이 32세, 평균 연봉 4800만원
삭제:     ***, 28세, 서울 강남구, ***, 연봉 5200만원
마스킹:   홍**, 28세, 서울 **구, 010-****-5678, 연봉 ****만원
범주화:   홍길동, 20대, 서울, 010-1234-5678, 연봉 5000~6000만원
```

📝 보충: **비식별화 5대 기법 — 세부 기법과 예시**

**1) 가명 처리 세부 기법:**

| 세부 기법 | 설명 | 예시 |
|----------|------|------|
| **휴리스틱 가명화** | 식별자를 임의 값으로 대체 | 홍길동 → 가나다 |
| **암호화** | 암호화 알고리즘으로 변환 | 홍길동 → 2Ks8#pQ |
| **교환법(Swapping)** | 레코드 간 값을 서로 교환 | A의 이름과 B의 이름을 바꿈 |

**2) 총계 처리 세부 기법:**

| 세부 기법 | 설명 | 예시 |
|----------|------|------|
| **총합(Aggregation)** | 합계, 평균 등 집계값만 제공 | 부서별 평균 연봉: 4,200만 원 |
| **부분 총계** | 그룹별 소계만 공개 | 20대 평균 점수: 78점 |
| **라운딩(Rounding)** | 올림/버림/반올림 처리 | 연봉 4,237만 원 → 4,200만 원 |
| **재배열(Rearrangement)** | 기존 데이터를 재배열하여 연결 불가하게 만듦 | 이름-나이-주소 매칭을 섞음 |

**3) 데이터 삭제 세부 기법:**

| 세부 기법 | 설명 | 예시 |
|----------|------|------|
| **식별자 삭제** | 직접 식별 가능한 정보 삭제 | 주민번호, 이름 컬럼 제거 |
| **식별자 부분 삭제** | 식별자 일부만 삭제 | 생년월일에서 "일" 삭제 → 1990-03 |
| **레코드 삭제** | 특이값을 가진 레코드 전체 삭제 | 120세 노인 데이터 행 자체 삭제 |

**4) 데이터 범주화 세부 기법:**

| 세부 기법 | 설명 | 예시 |
|----------|------|------|
| **감추기(Suppression)** | 특정 값을 '*' 등으로 대체 | 서울시 강남구 → 서울시 ** |
| **랜덤 라운딩** | 랜덤하게 올림/버림 | 나이 23 → 20대 |
| **범위 방법** | 범위로 치환 | 연봉 4,237만 → 4,000~4,500만 |

**5) 데이터 마스킹 세부 기법:**

| 세부 기법 | 설명 | 예시 |
|----------|------|------|
| **임의 잡음 추가** | 랜덤 노이즈를 데이터에 추가 | 키 175cm → 177cm (노이즈 +2) |
| **공백/대체** | 일부를 공백 또는 대체 문자로 변환 | 010-1234-5678 → 010-****-5678 |

**⚠️ 시험 포인트**:
- 10회 기출: "총계 처리된 데이터는 개인 단위 수치 계산이 가능하다" → **틀림** (집계된 수치만 제공)
- 10회 기출: "데이터 수가 적으면 개인 식별 가능성이 높아진다" → 맞음
- (💡 2025ver 보충) **재배열** 기법이 최근 시험에 출제됨

### 6.4 프라이버시 보호 모델 (K-익명성, L-다양성, T-근접성)

**한 줄 요약**: 비식별화된 데이터의 적정성을 평가하는 모델로, K → L → T 순으로 보호 수준이 올라간다.

**왜 이 세 가지인가?** K-익명성만으로는 공격에 취약해서 L-다양성이 등장했고, L-다양성도 한계가 있어서 T-근접성이 등장했다. 보안 허점을 발견할 때마다 더 강력한 모델이 나온 것이다.

```
K-익명성 ──→ L-다양성 ──→ T-근접성
(기본)      (중간)       (고수준)
보호 수준 ↑ ────────────────────→

K의 취약점을     L의 취약점을
L이 보완         T가 보완
```

| 모델 | 원리 | 취약점 | 핵심 키워드 |
|------|------|--------|-----------|
| **K-익명성** | 같은 값이 K개 이상 존재하게 하여 결합 불가하게 만듦 | 동질성 공격, 배경 지식 공격에 취약 | "K명 이상 같은 값" |
| **L-다양성** | 민감 정보의 다양성을 높여 추론 가능성 낮춤 | 쏠림 공격, 유사성 공격에 취약 | "L종류 이상 다양하게" |
| **T-근접성** | 민감 정보의 분포를 낮춰 추론 가능성을 더욱 낮춤 | - | "분포가 전체와 비슷하게" |

**취약점 → 보완 관계**:
- K-익명성의 한계(동질성/배경지식 공격) → L-다양성으로 보완
- L-다양성의 한계(쏠림/유사성 공격) → T-근접성으로 보완

📝 보충: **프라이버시 보호 모델 — 구체적 예시 (병원 환자 데이터)**

**K-익명성 예시 (K=3):**

비식별화 전:
```
| 나이 | 우편번호 | 질병     |
|------|---------|---------|
| 28   | 13068   | 감기     |
| 28   | 13068   | 독감     |
| 28   | 13068   | 폐암     |
```

→ 같은 값(28세, 13068)이 3개 이상이므로 K=3 만족.

📝 **계산 예시 — K값 판정**: "아래 테이블에서 K-익명성의 K값은?"
같은 준식별자(나이, 우편번호) 조합을 가진 행의 **최소 개수**가 K값이다.
위 예시: (28, 13068) 조합이 3행 → **K=3**. 만약 (35, 13070) 조합이 2행뿐이면 → 전체 테이블의 K값은 **2** (가장 적은 쪽이 기준)
→ **문제**: 3명 모두 호흡기 계열 질환 → "28세 13068 거주자는 호흡기 질환"이라고 추론 가능 (**동질성 공격**)

```
동질성 공격의 원리:

  K=3 만족 ✓           BUT!
  ┌───┬───────┬───┐   모든 질병이 "호흡기"로 동질적
  │28 │ 13068 │감기│   → 구체적 질병은 몰라도
  │28 │ 13068 │독감│     "호흡기 질환"이라는 사실은
  │28 │ 13068 │폐암│     추론 가능!
  └───┴───────┴───┘   
```

**L-다양성 예시 (L=3):**

```
| 나이 | 우편번호 | 질병     |
|------|---------|---------|
| 2*   | 130**   | 감기     |
| 2*   | 130**   | 위염     |
| 2*   | 130**   | 골절     |
```

→ 민감 정보(질병)가 3종류로 다양 → L=3 만족.
→ **문제**: 질병이 모두 경증이면 "이 사람은 경증 질환"이라고 추론 가능 (**유사성 공격**)

```
유사성 공격의 원리:

  L=3 만족 ✓           BUT!
  ┌───┬─────┬───┐   3종류지만 모두 "경증"으로 유사
  │2* │130**│감기│   → 구체적 질병은 몰라도
  │2* │130**│위염│     "경증 질환"이라는 사실은
  │2* │130**│골절│     추론 가능!
  └───┴─────┴───┘   
```

**T-근접성 예시:**

→ 민감 정보의 **분포**가 전체 데이터의 분포와 유사하도록 조정
→ 전체 환자 중 암 환자가 10%라면, 각 그룹에서도 암 환자 비율이 약 10%가 되어야 함
→ 특정 그룹에 암 환자가 몰려있으면 T-근접성 위반

```
T-근접성의 원리:

  전체 데이터 분포:    암 10%, 감기 50%, 골절 40%
  
  ✓ 그룹A: 암 12%, 감기 48%, 골절 40%  ← 전체와 비슷 (T-근접성 만족)
  ✗ 그룹B: 암 80%, 감기 10%, 골절 10%  ← 전체와 다름 (T-근접성 위반!)
```

**⚠️ 시험 포인트**:
- 현재까지는 각 모델의 개념만 물어봄
- 시험이 어려워지면 **사례(의료 환자 데이터)**를 주고 어떤 모델인지 구분하는 문제 가능
- 정부 가이드라인에서 의료 환자 데이터로 사례를 제시했으므로, 해당 사례로 공부 추천

**시험 출제 예시**: "K-익명성을 만족하지만, 동일 그룹 내 민감 정보가 모두 같은 값인 경우 발생하는 공격은?" → **동질성 공격** → L-다양성으로 보완

### 6.5 차등 정보 보호

**한 줄 요약**: 대량 데이터에 노이즈(오차)를 추가하여, 개인 식별은 불가하지만 패턴은 발견 가능하게 만드는 기법.

**왜 K-익명성/L-다양성과 다른가?** K-익명성 계열은 "데이터를 묶거나 일반화"하는 방식이고, 차등 정보 보호는 "데이터에 노이즈를 추가"하는 방식이다. 접근법 자체가 다르다.

- **섭동(Perturbation)**: 원래 데이터에 살짝 노이즈(잡음)를 섞는 것. 비유하면 **설탕물에 소금 한 꼬집을 넣어서 정확한 농도를 모르게 하는 것**. 개인 하나하나는 파악 불가하지만, 전체적인 "단맛" 경향은 알 수 있다.
- 이중 지수 분포(**라플라스 분포**) 등의 수학적 기법으로 노이즈 크기를 조절
  - 라플라스 분포란? 평균 0을 중심으로 좌우 대칭인 종 모양 분포. 노이즈를 추가할 때 **너무 크지도 작지도 않게** 자연스럽게 조절해주는 역할. 정규분포보다 꼬리가 두꺼워서 가끔 큰 노이즈도 섞임

```
차등 정보 보호의 원리:

  원본 데이터:  100, 200, 150, 300, 250
  노이즈 추가:  +3,  -5,  +7,  -2,  +1
  결과 데이터:  103, 195, 157, 298, 251

  → 개인 값은 정확히 알 수 없지만
  → 전체 평균은 거의 동일 (원본 200 vs 결과 200.8)
  → 통계적 패턴은 유지!
```

그래서 실제로 어떻게 쓰이냐면... 애플이 iOS 사용자 행동 데이터를 수집할 때 차등 정보 보호를 사용한다. 개별 사용자가 어떤 이모지를 사용하는지는 알 수 없지만, "전체적으로 어떤 이모지가 인기 있는지"는 파악 가능.

**⚠️ 시험 포인트**:
- 차등 정보 보호 = 노이즈 추가 방식 (K-익명성/L-다양성과 다른 접근)
- 개인정보는 보호하면서 통계적 패턴은 유지하는 게 핵심

### 6.6 데이터 품질 기준

**한 줄 요약**: 데이터의 품질을 판단하는 7가지 기준.

**왜 품질이 중요한가?** "Garbage In, Garbage Out" — 쓰레기 데이터를 넣으면 쓰레기 결과가 나온다. 아무리 좋은 분석 모델도 데이터 품질이 나쁘면 의미 없다.

| 품질 기준 | 의미 | 이게 안 되면? | 검사 예시 |
|----------|------|-------------|----------|
| **유효성** | 정의된 형식 및 범위를 충족 | 주민번호에 알파벳이 들어가는 꼴 | "나이" 컬럼에 -5나 300이 있는지 |
| **완전성** | 누락 없이 존재 | 고객 100명 중 30명 연락처가 빈칸 | 빈칸(NULL) 비율 확인 |
| **일관성** | 데이터가 시스템 간 일관됨 | A시스템엔 "서울", B시스템엔 "Seoul" | 동일 고객의 정보가 시스템마다 같은지 |
| **정확성** | 데이터가 실제와 일치 | 키 175cm인데 1750cm으로 입력 | 실제 값과 저장된 값이 일치하는지 |
| **유일성** | 중복 없이 유일 | 같은 고객이 3번 등록되어 분석 왜곡 | 중복 레코드 존재 여부 |
| **적시성** | 필요한 시점에 제공 | 어제 주가로 오늘 투자 결정 불가 | 데이터 갱신 주기가 적절한지 |
| **접근성** | 필요 시 쉽게 접근 가능 | 데이터가 있는데 찾을 수 없음 | 권한 있는 사람이 데이터에 접근 가능한지 |

> **7가지 기준 빠르게 외우기**: "유(효)완일정유(일)적접" — 유효성, 완전성, 일관성, 정확성, 유일성, 적시성, 접근성

📝 **계산 예시 — 데이터 품질 측정**:
- **완전성 비율** = (NULL이 아닌 레코드 수 / 전체 레코드 수) x 100%
  - 고객 1,000명 중 연락처가 비어있는 레코드 200개 → 완전성 = 800/1000 x 100 = **80%**
- **유일성 비율** = (중복 제거 후 레코드 수 / 전체 레코드 수) x 100%
  - 전체 5,000건 중 중복 500건 → 유일성 = 4500/5000 x 100 = **90%**

**⚠️ 시험 포인트**:
- 10회 기출: "완전성 — 쉽게 찾을 수 있어야 한다" → **틀림** (완전성 = 누락 없이 존재, 쉽게 찾는 건 "접근성")
- 10회 기출: "유효성 — 정의된 형식 및 범위를 충족" → 맞음
- "데이터 품질 기준이 아닌 것은?" 형태 출제
- **품질 진단 및 개선 절차** 순서도 시험에 나온 적 있음 → 반드시 기억

**시험 최대 함정**: 완전성 vs 접근성 혼동! **완전성** = "데이터가 빠짐없이 존재하는가", **접근성** = "존재하는 데이터에 쉽게 접근할 수 있는가". 둘 다 "있어야 한다"는 느낌이지만, 완전성은 데이터 자체의 존재 여부, 접근성은 접근 경로의 문제.

### 6.7 분산 파일 시스템 (HDFS)

**한 줄 요약**: 여러 컴퓨터에 데이터를 나누어 저장하는 파일 시스템. 하둡의 핵심 프로젝트.

**핵심 설명**:

#### GFS → HDFS

- **GFS (Google File System)**: 구글이 설계한 분산 파일 시스템
- **HDFS (Hadoop Distributed File System)**: GFS를 기반으로 개발된 **오픈소스** 분산 파일 시스템

비유하면 구글이 "분산 저장" 비법(GFS)을 만들었고, 이를 참고해서 누구나 쓸 수 있는 오픈소스 버전(HDFS)이 나온 것.

#### HDFS 구조

```
┌──────────────────────────────────────┐
│         마스터 노드 (NameNode)         │  ← 관리자: "어떤 데이터가 어디에 있는지" 관리
│         "데이터 위치 지도"              │
└──────────────┬───────────────────────┘
               │ 지시/관리
    ┌──────────┼──────────┐
    ↓          ↓          ↓
┌───────┐ ┌───────┐ ┌───────┐
│DataNode│ │DataNode│ │DataNode│  ← 실제 데이터 저장/처리
│(블록1) │ │(블록2) │ │(블록3) │
└───────┘ └───────┘ └───────┘
  슬레이브 노드들 (여러 대의 컴퓨터)
```

| 구성 요소 | 역할 | 비유 |
|----------|------|------|
| **마스터 노드(NameNode)** | 관리/조율 | 택배 본부 (배송 어디로 갈지 관리) |
| **슬레이브 노드(DataNode)** | 실제 데이터 처리/저장 | 각 지역의 택배 창고 |

- **블록 단위** 관리: **하둡 1.x는 64MB**, **하둡 2.x 이후는 128MB**가 기본 블록 크기. 사용자 변경 가능
- 분산 처리의 장점: 시스템 과부하 해소, 병목 현상 해소
- **복제본(Replication)**: 장애 대비를 위해 각 블록을 기본 **3개**씩 복제하여 다른 DataNode에 저장. 하나가 고장나도 나머지에서 데이터 복구 가능

📝 **계산 예시 — HDFS 블록 수**: 
- 1GB 파일을 하둡 2.x(블록 128MB)에 저장하면? → 1,024MB / 128MB = **8개 블록**
- 복제본 3개 기준 실제 저장 용량: 8 x 3 = **24개 블록분** (3GB 사용)

📝 보충: 분산 파일 시스템과 분산 데이터베이스는 **다른 개념**. 파일 시스템은 파일로 저장, DB는 정형화된 구조로 저장.

### 6.8 데이터베이스 — 관계형 DBMS vs NoSQL

| 구분 | 관계형 DBMS | NoSQL |
|------|-----------|-------|
| 데이터 형태 | 정형 (테이블) | 비정형 |
| 무결성 | 보장 | 유연성/가용성 중시 |
| 예시 | Oracle, MySQL | MongoDB, Cassandra |
| 시대 | 전통적 | 빅데이터 시대 |
| 비유 | 엑셀 시트 | 메모장/포스트잇 |

> **비교표에서 이 차이가 왜 중요한가?** 빅데이터 시대에는 영상, 로그, SNS 글 등 비정형 데이터가 폭발적으로 증가했다. 기존 RDBMS는 이런 데이터를 효율적으로 저장할 수 없어서 NoSQL이 등장한 것. 시험에서 "빅데이터 시대에 NoSQL이 등장한 이유"를 물어볼 수 있다.

**NoSQL의 4가지 유형**: 키-값, 문서, 컬럼 패밀리, 그래프 (세부 유형도 최근 출제 시작)

| NoSQL 유형 | 구조 | 대표 제품 | 비유 |
|-----------|------|----------|------|
| **키-값(Key-Value)** | 키:값 쌍 | Redis, DynamoDB | 사물함 (번호로 열면 내용물 나옴) |
| **문서(Document)** | JSON/XML 문서 | MongoDB | 파일 캐비닛 (문서별 관리) |
| **컬럼 패밀리** | 컬럼 기반 저장 | Cassandra, HBase | 엑셀인데 행마다 컬럼이 다를 수 있음 |
| **그래프(Graph)** | 노드+관계 | Neo4j | SNS 친구 관계도 |

> **4가지 유형 구분 팁**: "키로 찾으면 키-값, 문서로 저장하면 문서형, 열 기반이면 컬럼, 관계를 보면 그래프". 시험에서 "SNS 친구 관계 분석에 적합한 NoSQL 유형은?" → 그래프 DB.

### 6.9 저장소 (Storage)

| 유형 | 정식 명칭 | 연결 방식 | 특징 | 비유 |
|------|----------|----------|------|------|
| **DAS** | Direct Attached Storage | 물리적 직접 연결 | 서버에 직접 붙임 | USB 외장하드 |
| **NAS** | Network Attached Storage | 네트워크 연결 | 여러 컴퓨터가 접근 가능 | 공유 폴더 (네트워크 드라이브) |
| **SAN** | Storage Area Network | 광케이블 고속 네트워크 | 특수 목적, 고성능 | 전용 고속도로로 연결된 대형 창고 |

```
DAS:  [서버]──[저장소]     (1:1 직접 연결)
NAS:  [서버A]──┐
      [서버B]──┼──[네트워크]──[저장소]  (N:1 네트워크 연결)
      [서버C]──┘
SAN:  [서버A]──┐
      [서버B]──┼──[광케이블 네트워크]──[저장소]  (고속 전용 네트워크)
      [서버C]──┘
```

### 6.10 병렬 DBMS와 분산 DBMS

| 구분 | 특징 | 비유 |
|------|------|------|
| **병렬 DBMS** | 데이터를 병렬적으로 빠르게 처리 | 여러 계산원이 동시에 계산 |
| **분산 DBMS** | 여러 DB를 네트워크로 연결하여 하나의 DB처럼 사용 | 여러 지점을 하나의 가게처럼 운영 |

**분산 DBMS 비유**: 서울/부산/대전에 각각 DB가 있지만, 네트워크로 논리적 연결 → 사용자에게는 하나의 DB처럼 느껴짐

```
【병렬 DBMS】                    【분산 DBMS】
                                
 ┌──────────────────┐           서울DB ── 부산DB
 │    하나의 DB       │               \   /
 │  [CPU1][CPU2][CPU3]│                대전DB
 │  동시에 처리       │           네트워크로 연결 →
 └──────────────────┘           사용자에겐 하나로 보임
  핵심: 속도           핵심: 분산 + 통합
```

> **병렬 vs 분산 차이가 왜 중요한가?** 병렬은 "한 곳에서 여러 CPU로 빠르게", 분산은 "여러 곳에 흩어진 것을 하나처럼". 시험에서 둘을 혼동하게 하는 문제가 나올 수 있다.

(💡 2025ver 보충) 병렬 DBMS의 3가지 구조: 공유 메모리, 공유 디스크, Shared Nothing

### 6.11 데이터 웨어하우스, 데이터 마트, 데이터 레이크

**한 줄 요약**: 기업의 데이터를 통합 저장하는 창고(웨어하우스), 소규모 분점(마트), 비정형 호수(레이크).

**이 주제는 정말 중요하다. 시험에 정말 자주 출제된다.**

#### 데이터 웨어하우스 (DW)

비유: 기업 내 여러 부서(인사, 재무, 기술 등)에 흩어진 DB들을 **하나의 큰 창고**에 통합 저장. 경영진이 한눈에 인사이트를 얻을 수 있게 해줌.

그래서 실제로 어떻게 쓰이냐면... 쿠팡의 마케팅팀, 물류팀, CS팀이 각각 DB를 갖고 있다. 이걸 데이터 웨어하우스에 통합하면, 경영진이 "이번 달 전체 매출, 반품률, 고객 만족도"를 한 번에 볼 수 있다.

**4가지 특성**:

| 특성 | 설명 | 쉬운 표현 |
|------|------|----------|
| **주제 지향성** | 분석 목적에 맞게 설정 | 주제별로 데이터 정리 |
| **통합성** | 형식을 일관화하여 정형 데이터로 통합 | 여기저기서 모아서 하나로 |
| **시계열성** | 과거~현재 히스토리를 시간순으로 저장 | 시간 흐름을 볼 수 있음 |
| **비휘발성** | 읽기 전용, 수정/삭제 불가 | 넣기만 하고 바꿀 수 없음 |

**⚠️ 핵심 함정**: "휘발성"이라고 낚시하는 보기 주의! 데이터 웨어하우스는 **비**휘발성!

```
DW 4특성 시각화:

  ┌─────────────────────────────────────┐
  │         데이터 웨어하우스              │
  │                                     │
  │  [주제 지향성]   "고객", "매출" 등    │
  │  주제별 정리      주제 중심으로 구성    │
  │                                     │
  │  [통합성]         부서A + 부서B        │
  │  하나로 통합       형식 일관화          │
  │                                     │
  │  [시계열성]       2023 → 2024 → 2025  │
  │  시간순 저장       과거 이력 보존       │
  │                                     │
  │  [비휘발성]       읽기만 O             │
  │  수정/삭제 X       한번 넣으면 끝       │
  └─────────────────────────────────────┘
```

**DW 구성 요소**:
- **ETL**: 각 부서 DB에서 데이터를 추출 → 변환 → 적재 (6.1절에서 배운 내용!)
- **ODS (Operational Data Store)**: 임시 저장소. ETL 후 DW에 보내기 전에 임시 저장 (시험 출제됨)

```
ETL과 DW의 관계:

[부서A DB]──┐                    ┌──────────┐
[부서B DB]──┼──[ETL]──→[ODS]──→│    DW     │
[부서C DB]──┘  추출/변환/적재  임시저장   │ (최종 창고) │
                                └──────────┘
```

**⚠️ 시험 포인트**:
- 10회 기출: "데이터 웨어하우스의 특징으로 볼 수 없는 것은?" → **주제지향성, 통합성, 시계열성, 비휘발성** 외의 것을 고르면 됨
- 4가지 특성 반드시 암기
- ODS = 임시 저장소

#### 데이터 마트 (Data Mart)

- 데이터 웨어하우스의 **소규모 버전**
- **특정 목적/부서**를 위해 사용
- 비유: 큰 창고(DW)에서 마트(상점)에 물건을 보내는 것

그래서 실제로 어떻게 쓰이냐면... DW에 회사 전체 데이터가 있다면, 마케팅팀용 데이터 마트에는 마케팅에 필요한 데이터만 뽑아서 넣어둔다.

#### 데이터 레이크 (Data Lake)

- **비정형 데이터**를 포함하여 모든 데이터를 그대로 저장하는 호수
- 비유: 호수에 데이터를 그냥 다 던져 넣음 (정제하지 않고 원시 상태로)
- 하둡(Hadoop)과 연계하여 처리

```
세 가지 저장소 비교:

  [데이터 웨어하우스]     [데이터 마트]        [데이터 레이크]
  ┌──────────────┐     ┌──────────┐       ┌──────────────┐
  │ 전사 통합 창고  │     │ 부서별 매대 │       │ 원시 데이터 호수│
  │ 정형 데이터만   │     │ 특정 주제   │       │ 모든 형태 OK  │
  │ 정리/정돈됨    │     │ 소규모     │       │ 원시 상태 그대로│
  │ RDBMS 기반    │     │ DW에서 추출 │       │ 하둡 기반     │
  └──────────────┘     └──────────┘       └──────────────┘
     "백화점 창고"         "편의점"            "수산시장"
```

| 비교 | 데이터 웨어하우스 | 데이터 레이크 |
|------|----------------|-------------|
| 데이터 형태 | 정형 데이터 | 정형 + 비정형 모두 |
| 구조 | 정형화된 구조 | 원시 상태 그대로 |
| 목적 | 경영 의사결정 | 다양한 분석 |
| 기반 기술 | RDBMS | 하둡(Hadoop) |

> **DW vs 데이터 레이크 차이가 왜 중요한가?** 시험에서 둘을 비교하는 문제가 자주 출제된다. 결정적 차이: DW는 "정리된 정형 데이터만", 레이크는 "원시 상태 그대로 모든 데이터".

### 6.12 하둡(Hadoop) 생태계

**한 줄 요약**: 여러 컴퓨터를 하나로 묶어 대용량 데이터를 처리하는 오픈소스 솔루션.

#### 코어 프로젝트

| 프로젝트 | 역할 | 비유 |
|---------|------|------|
| **HDFS** | 분산 **저장** (여러 블록으로 분산 저장) | 여러 창고에 나눠서 보관 |
| **MapReduce** | 분산 **처리** (병렬 처리로 속도 향상) | 여러 사람이 나눠서 일함 |

> **HDFS와 MapReduce 구분 핵심**: HDFS = **저장**, MapReduce = **처리**. "S"torage = HDFS, "R"educe = 처리.

#### MapReduce 동작 원리

1. **Map 단계**: 데이터를 키(Key)와 밸류(Value)로 변환
2. **Reduce 단계**: 변환된 결과를 집계

```
MapReduce 예시: "문서에서 단어 빈도 세기"

원본: "사과 배 사과 포도 배 사과"

  【Map 단계】                    【Reduce 단계】
  사과 → (사과, 1)               사과: 1+1+1 = 3
  배  → (배, 1)                  배:  1+1   = 2
  사과 → (사과, 1)               포도: 1     = 1
  포도 → (포도, 1)
  배  → (배, 1)                  결과: {사과:3, 배:2, 포도:1}
  사과 → (사과, 1)
  (각각 키:값으로 변환)           (같은 키끼리 모아서 합산)
```

#### 서브 프로젝트 (하둡 생태계)

다양한 서브 프로젝트가 존재하며, 시험이 어려워지면 세부 내용도 출제 가능.

| 서브 프로젝트 | 역할 | 한 줄 비유 |
|-------------|------|----------|
| **Hive** | SQL로 HDFS 데이터 조회 | "하둡의 엑셀 필터" |
| **Pig** | 스크립트 기반 데이터 처리 | "하둡의 매크로" |
| **Spark** | 메모리 기반 초고속 처리 | "MapReduce의 터보 버전" |
| **HBase** | 실시간 읽기/쓰기 DB | "하둡 위의 NoSQL DB" |
| **Sqoop** | RDBMS ↔ HDFS 데이터 이동 | "DB와 하둡 사이의 택배기사" |
| **Flume** | 실시간 로그 수집 | "데이터 수도관" |
| **Oozie** | 작업 스케줄링/워크플로우 | "하둡의 알람 시계" |
| **ZooKeeper** | 분산 시스템 조율/관리 | "오케스트라 지휘자" |

```
하둡 생태계 전체 구조:

  ┌──────────────────────────────────────────┐
  │              하둡 생태계                    │
  │                                          │
  │  ┌─────┐  ┌─────┐  ┌───────┐            │
  │  │Hive │  │ Pig │  │ Spark │  ← 분석/처리 │
  │  └──┬──┘  └──┬──┘  └───┬───┘            │
  │     │        │         │                 │
  │  ┌──┴────────┴─────────┴──┐              │
  │  │      MapReduce          │  ← 분산 처리 │
  │  └────────────┬────────────┘              │
  │               │                          │
  │  ┌────────────┴────────────┐              │
  │  │         HDFS             │  ← 분산 저장 │
  │  └─────────────────────────┘              │
  │                                          │
  │  Sqoop↔RDBMS  Flume←로그  ZooKeeper(관리) │
  └──────────────────────────────────────────┘
```

**⚠️ 시험 포인트**:
- HDFS와 MapReduce는 시험에 정말 많이 출제
- HDFS = 저장, MapReduce = 처리 구분
- (💡 2025ver 보충) 하둡 서브 프로젝트의 세부적인 내용까지 물어볼 수 있으므로, 여력이 되면 학습

### 6장 연습문제

**Q1. 다음 중 반정형 데이터에 대한 설명으로 올바르지 않은 것은?**
1. 스키마는 없지만 메타데이터를 포함한다
2. XML, JSON, HTML이 대표적인 예시다
3. 태그값을 통해 의미 분석이 가능하다
4. 고정된 스키마를 가지므로 구조 변경이 어렵다

> **정답: 4**
> 해설: 반정형 데이터는 고정된 스키마가 **없고**, 태그를 통해 구조를 표현하므로 구조 변경이 **유연하다**. (4)는 정형 데이터의 특징. 10회 기출에서 "구조 변경이 어렵다"를 반정형 데이터 설명으로 제시하여 함정을 만든 바 있다. **왜 (1)이 맞는가?** 반정형 데이터의 핵심은 "스키마 없음 + 메타데이터 있음". XML의 태그가 바로 메타데이터 역할.

**Q2. 데이터 웨어하우스의 4가지 특성에 해당하지 않는 것은?**
1. 주제 지향성
2. 휘발성
3. 통합성
4. 시계열성

> **정답: 2**
> 해설: 데이터 웨어하우스는 **비**휘발성이다! 한번 저장되면 읽기 전용으로 수정/삭제가 불가. "휘발성"이라고 낚시하는 보기는 단골 함정. 4가지 특성: 주제지향성, 통합성, 시계열성, 비휘발성. **이 문제가 반복 출제되는 이유**: "비"를 빼면 정반대 의미가 되는데, 시험 긴장 상태에서 "비"를 놓치기 쉽기 때문.

**Q3. ETL에서 "T(Transform)"에 해당하는 활동은?**
1. 특정 소스에서 데이터를 꺼내는 작업
2. 데이터를 우리 기업의 형식에 맞게 변환하는 작업
3. 변환된 데이터를 데이터베이스에 저장하는 작업
4. 데이터의 품질을 검증하는 작업

> **정답: 2**
> 해설: E(Extract)=추출(꺼냄), T(Transform)=변환(우리 기업에 맞게 변환), L(Load)=적재(DB에 저장). (4)는 별도의 데이터 품질 관리 활동이며 ETL의 T가 아니다. **왜 (4)가 교묘한가?** 변환 과정에서 품질 검증도 할 수 있지만, T의 핵심은 "형식 변환"이지 "품질 검증"이 아니다.

**Q4. (심화) 다음 중 K-익명성, L-다양성, T-근접성에 대한 설명으로 올바르지 않은 것은?**
1. K-익명성은 동질성 공격에 취약하다
2. L-다양성은 K-익명성의 한계를 보완한다
3. T-근접성은 민감 정보의 분포를 전체 데이터와 유사하게 맞춘다
4. L-다양성은 T-근접성의 한계를 보완하기 위해 등장했다

> **정답: 4**
> 해설: 순서가 반대다! K → L → T 순서로 보호 수준이 올라가므로, **T-근접성**이 **L-다양성**의 한계를 보완한 것이다. (4)는 방향이 반대. K의 한계 → L이 보완, L의 한계 → T가 보완이 정확한 순서.

**Q5. (심화) 다음 상황에서 가장 적합한 저장소는?**

> 기업에서 정형 데이터뿐만 아니라 SNS 텍스트, 센서 로그, 영상 데이터를 원시 상태 그대로 모두 저장하여 향후 다양한 분석에 활용하고자 한다.

1. 데이터 웨어하우스
2. 데이터 마트
3. 데이터 레이크
4. 관계형 DBMS

> **정답: 3**
> 해설: "원시 상태 그대로", "비정형 데이터 포함", "모든 데이터" → 데이터 레이크. DW는 정형 데이터만 정리하여 저장, 마트는 DW의 소규모 버전, RDBMS는 정형 데이터 전용. 데이터 레이크만이 비정형을 포함한 모든 데이터를 원시 상태로 저장.
